ユーザーの依頼で、大きな構造ができていれば旧画面を使えるはずか、できないなら設計の抽象化の不足がどこにあるかを測った。

**旧画面が食べているもの。** `apps/web/village-debug.tsx` は `VillageRecording`（fixture、initialGrid、initialLand、events、decisions、terrainCommands、rulesetId）と、`VillageStatusReplay` が事象から再構成する `PersonStatus`（carried・home・market・field・ground の在庫 `InventoryItem` {id, kind, quantity, mass, ownerId, containerId, expiresDay, offered}、body {alive, energy, maxEnergy, hunger, cold, sleepDebt, mealHours, temperature, sheltered, activity, sleep, effort}）、格子 `GridMap` のセル位置、植物・動物・穀物の在庫、進行中の行為、判断履歴（`VillageDecisionRecord`、経験からの見込み）、売買を描く。行為者は S・F・C・B1・B2 の固定 id。

**できるか。** できる。骨格から旧画面の入力へ写す変換層を書けば、位置（連続座標をセルに量子化。家と木を sites に）、持ち物（人に付いた実を carried の InventoryItem に。kind は札 edible の値）、身体（栄養を energy に、意図を activity に。空腹・寒さ・睡眠・体温は 0）、事象（記録の law:kind を VillageEvent の種類に）、植物（木と実を plants に）は写せる。再生は `VillageStatusReplay` を通さず、刻みごとの写しを直接 statuses に入れるのが近い。見積りは変換層 300〜500 行。ただし旧画面は fixture・rulesetId・固定の行為者 id・格子・容器 id の命名（bag_、home_chest_、granary_）に結びついていて、変換層はそれらの名前を偽装することになる。旧画面を活かすより、骨格の画面を育てるほうが安い。

**検討で測れた、現在の設計の抽象化の不足。**

| 旧画面が求めるもの | 骨格の現状 | 評価 |
|---|---|---|
| 家・地面・倉という場所の在庫 | 家は人の属性 homeX・homeY で、事物でない。地面・倉も無い | 設計の矛盾。「すべてが事物」に反する。家を定義として置き、持ち物を家に付け替えられるようにする → **第30回で解消**（定義 home、法則 stow、関係 rel[home].home）。地面・倉は未着手 |
| 容器の容量（mass・capacity） | 付属の鎖はあるが、受ける側の受容の上限が無い | 既知の未実装。要求 → 解決の受ける側の縮小として入る |
| 時刻 t の状態の再生（録画） | 記録 ledger はあるが、初期状態の保存と、記録を apply し直す再生が無い | 仕組みの不足。決定的で書き込みは apply だけなので、初期状態＋記録で再生できるはず。小さな追加 → **第30回で解消**（World.save・load・replay） |
| 判断履歴と経験からの見込み | 意図が変わった事象だけ。心がなぜそう決めたか、何を見込んだかの記録が無い | 情報層の不足。判断の記録は事象の一種として置ける。判断方式の内部は細部だが、記録の形は構造 |
| 身体の値（空腹・寒さ・睡眠・体温・労作） | 栄養と胃だけ | データの不足で、設計の不足ではない。資源と属性を足す |
| 格子の地形・障害・経路 | 連続座標と直線移動。地形は無い | 空間の表現が未決。地形を事物にするか、場の属性にするかは決めていない |
| 売買・所有・貨幣 | 無い | 既知の未決（記録・コミットメント） |
| 行為者の固定 id、fixture | 定義から任意の数を生成 | 旧画面側の制限。骨格の問題ではない |

**結論。** 旧画面の再利用は変換層で可能だが、旧画面の前提（fixture・固定 id・格子・容器名）を骨格に逆流させるので採らない。検討で測れた設計の不足は四つ（場所が事物でない、受容の上限、録画と再生、判断の記録）で、いずれも大きな構造の枠内で足せる。空間の表現は未決として残す。このうち「家を事物にする」と「初期状態＋記録の録画と再生」は第30回で実装し、残りは受容の上限と判断の記録。
