# 3日経済を物体・能力モデルへ移す実装前監査

状態: 2026-09-26の設計・コード照合。以下のL0/L1の3日fixture契約は、新しい独立`local_food_v2`で実装・検証済み。旧`local_food_v1`は従来の`FoodLot`/`CashContainer`/固定時刻相のまま残す。新方式の本編90日への接続、共通ルーティンランナー、性能測定は未着手。[物体モデル](PHYSICAL_OBJECT_MODEL.md)、[能力エージェント](CAPABILITY_AGENTS_DESIGN.md)、[E1契約](ECONOMY_E1_CONTRACT.md)を対象にする。

## 結論と3日fixtureの境界

新しい抽象型を宣言するだけでは実装を開始できない。**型別の初期物体と容量、時刻ごとの親子関係、能力提案からTask/Actionへの接続、原子的な移転、保存版と受入値**を固定する必要がある。この文書で3日fixture用の仮決定を置き、L0の物体/能力契約試験→L1のE1移行を実装可能な単位にする。

3日経済の基準は現行の20人・4世帯、農場/市場/4軒、食料60生産/60消費、配送21/21/18、世帯→事業の支払120通貨を維持する。**基準fixtureは荷車1台・運搬人Cのまま**。馬、複数馬車、技能の売買、賃金、体力回復をこの基準へ同時追加しない。二台の馬車と馬の牽引は[能力設計の独立L0対照](CAPABILITY_AGENTS_DESIGN.md#二台の馬車を積んで運ぶ例)で検証し、その後に同じ能力境界をE1のCへ接続する。これで抽象基盤を単一荷車への特化だけで合格させない。

## 実装前に固定する五つの契約

| 論点 | 現行との差・未決定だった点 | 3日fixtureの仮決定 |
| --- | --- | --- |
| 物体と初期配置 | 食料と現金の場所が別形式。財布/荷車/家の親子関係がない | 下表の型と実体IDを版付きコンテンツで定義。物体の`parentId`を所在の正本にする |
| 重量と容量 | 食料5、現金20、荷車21を新しい負荷単位へどう写すか未定 | 食料1・通貨1を各1負荷点、袋/財布/荷車の自重0。人の内容物上限25、タグ上限は食料5/通貨20。施設と荷車のタグ上限を旧値に一致させる |
| 能力と時刻 | Cの`carry_food`は固定コード分岐。いつ提案/再計画し、誰がActionを出すか未定 | Cだけ`transport.food.v1`を持つ。05:30の依頼受諾後に既定便を提案、農場で実物を見た12:30に積載量を再提案。本人IDのTask/Actionから実行する |
| 原子的な資産操作 | 旧`settlePurchase`は食料減少と現金移動が段階的。失敗時に片側だけ変わる危険がある | 出発前検査→積載/出発、販売の食料/現金/所有権変更をそれぞれ一括確定。失敗は理由Eventのみ、食料を無言で戻さない |
| 版・受入 | 新しい物体ID/Eventで旧ハッシュとセーブは一致しない | 新モード版を`schemaVersion:3`/`economicMode:"local_food_v2"`/`engineVersion:"0.4.0-e1"`、コンテンツ版を`schemaVersion:2`とする。旧E1セーブは明示的な版違いとして拒否し、同じ版の保存再開/seed+Command再実行を一致させる |

負荷点1は3日fixtureの**抽象単位**で、現実のkgを主張しない。自重0は旧E1の移動費用と受入値を保つための仮値である。荷車の空荷でも旧`cartEffortPerKm`による体力費用は発生する。財布や車両の自重・馬の飼葉は別の対照から追加する。人の25負荷点という合計上限は、旧「食料5かつ現金20」を同時に満たすためで、タグ別上限を緩めない。

### 物体型と初期実体

| 種類/実体 | 直接入れられる子と制約 | 初期の親・所有者 |
| --- | --- | --- |
| 世界・町・農場・市場・家H0〜H3 | siteは人/荷車/建物/保管具を受け入れる。画面矩形は表示用で道路距離2kmとは別 | 世界が根。町に市場/家、農場は世界直下。siteは非所有物 |
| 移動中の`transit:<journeyId>` | 同じ便の人/荷車を受け入れる一時的な通行空間。出発時刻・到着時刻・両端siteを持つ | 世界が親。到着時に子を目的siteへ移し、空になった時点で閉じる。中間表示位置は時刻から導出 |
| 人物F0〜F6/B0〜B3/S/C/D0〜D6 | 財布・食料袋などを携行。内容物25負荷点、食料5、通貨20 | 全員が既存の家を親にする。Person IDは変更しない |
| 農場食料庫・市場食料庫・各家の食料庫 | 食料100/60/10。対象外の財は拒否 | 農場/市場/家が親。所有と保管場所は別。庫そのものは協同事業/世帯所有 |
| 家H0〜H3の金庫・買物係B0〜B3の財布・市場金庫・H0の予備箱 | 通貨100/20/200/100。現金は子の数量ロット | 金庫は家、財布は各B、売上金庫は市場、予備箱はH0の家。所有者は現行E1に合わせる |
| 荷車`cart_1` | 食料21、内容物21負荷点。荷車の物理的所在は親、牽引者はMovement/Task | 初期は市場。車両所有者は協同事業 |
| 食料・通貨ロット | 同質の数量物体。子は持てない。所有者と親を別に保持 | 初期食料0。各家金庫に世帯所有の現金40、市場金庫/予備箱/財布は0 |

siteを根とした親子関係と、所有/世帯/職場所属を混同しない。`cart_1`がCと移動するとき、Cと荷車は同じ`transit:<journeyId>`の子になり、食料は荷車の子に留まる。Cを荷車の所有者や荷車をCの子に自動変更しない。袋や財布の中身を動かさず人を移す。`FoodLot.place="cargo:<shipmentId>"`は荷車を親にするので、便と物理車両の一対一の関係を推測せずに済む。既存の金庫/財布/金銭箱IDは維持し、食料庫は`store_farm`、`store_market`、`store_H0`〜`store_H3`を初期IDとする。生産・分割ロットと通行空間の新IDはseed・Command・確定順から決定的に採番する。

### 時刻・提案・効果の対応

現行の時刻表を受入基準とする。05:00〜05:30に買物係の発注と売り手の補充依頼、05:30にCの仕事受諾/既定便提案、06:00〜07:00にCと荷車が市場→農場、12:00に農民の生産確定、12:00〜12:30に荷役Task、12:30にCが見た農場在庫から`min(依頼21, 利用可能在庫, 荷車の空き)`を提案、12:30〜13:30に農場→市場、13:30〜14:00に荷下ろし/受領、14:00〜15:00に4世帯の受渡し、18:00〜19:00に人物別食事とする。買物係は現金を家の金庫から財布へ移してから市場へ行く。売買後の食料は本人の袋、帰宅後は家の食料庫にある。

ルーティンは上記のTask順と期限を管理する。Cの能力エージェントは物理効果を直接起こさず、`transport.food.v1`の提案を一つ選ぶ。3日fixtureの人格による引受は現行と同じ決定的ルールでよいが、Cが拒否/不在なら便は出ない。農場の真の在庫はCが到着/観察するまで提案入力へ入れない。荷車の供用能力は物体型の21を参照し、`CapabilityInstance`へ21を重複保存しない。提案には本人ID、Task ID、対象物体ID、数量、所要時刻、期待費用、根拠Event ID、モデル版を記録する。安定ID順で選んだ提案だけをsimへ渡す。

12:30に荷車の積載と出発を同じsim操作で事前検査する。体力不足/過積載/荷車不在なら食料は農場の庫に残り、Taskと便は失敗Eventを残す。積載後の道中障害は次の拡張で扱い、その時は貨物を車上の現在位置に留める。食料が0なら空車の帰路を別の移動として行う。販売は市場庫の食料と買物係の財布の現金を両方予約し、所定の15分枠終了時に食料→袋と現金→市場金庫を同時確定する。買物係が市場にいない、売り手がいない、容量が足りない、拘束済み財を再利用しようとする場合は成立しない。金庫→財布の持出しも、財布容量・本人の運搬余力・出発可能性を一括で検査してから確定する。失敗時には金を金庫に残す。食事はその人物が家にいて、世帯所有の食料が家の庫にある場合だけ成功する。

既存の体力式と移動時間は3日基準で維持する。積荷の数量は物体木から導出し、`Journey.foodLoad`/`cashLoad`を正本にしない。式に必要な「食料何単位・現金何単位」はタグ別数量から得る。新しい荷車/馬の牽引式をこの単一荷車基準へ混ぜない。

## 受入条件と後回しにするもの

- L0: 財布→人→家、食料→荷車→通行空間の親子関係、重量/タグ別容量、循環拒否、所有権と保管の独立、失敗時の原子性をテストする。別fixtureで二台の馬車・馬2頭なら150負荷点が運べ、馬1頭/悪路/荷役人欠勤では一便が成立しないことを検証する。
- L1: 新版E1で3日60生産/60消費、21/21/18輸送、12件の販売/120通貨移転、全20人×3日の食事、所有者別現金・全食料の保存式を確認する。運搬人欠勤、買物係の資金不足、農民欠勤、二重予約、疲労、車両不在の対照が物体位置と結果を変える。人物/Task/物体/Eventの因果リンク、コンテンツの型・参照・循環検証、同一版での安定したEvent順を検査する。
- 保存と画面: 積載中と移動中のセーブを新形式で再開し、seed+Command再実行と同じEvent/物体木になる。デバッグ画面では各物体の親、所有者、現在地、積載/上限、能力と最終行動を選択できる。旧E1セーブの拒否は明示エラーにする。本編90日ゲームは旧世界を維持して回帰テストを行う。

賃金/技能市場、複数車両を使う3日経済、馬の飼葉・修繕、体力回復、道路障害、人格v2の全面実装、軍補給、本編経済統合は今回の3日基準の受入に含めない。これらを空Eventや初期資金で達成済みにしない。E1の新モデルの性能は計測するまで未達扱いとする。

## L1実装結果

`packages/sim/local-economy-v2.ts`は現行E1と同じ20人・4世帯の時間表で動くが、食料/現金/所在地を`PhysicalState`だけに保存する。人物別Task、Cの提案/再提案、到着・荷役・売買・食事は原因Eventを残す。`packages/content/economy-e1-v2.json`の物体型はコンテンツ検査対象。`npm run economy:e1:v2 -- baseline`と`/?e1=v2`から観察できる。基準3日では60食生産/消費、配送21/21/18、12件販売、120通貨移転。旧形式と内部Eventが異なるためworldHashは別値とし、同じ新版での保存再開・Command再実行の一致を試験した。性能は未計測。
