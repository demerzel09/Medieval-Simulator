# データ駆動のルーティン設計

状態: 設計案。ゲームコードとコンテンツ形式は未変更。[認知・行動インターフェースv2](AGENT_INTERFACES_v2.md)、[社会的慣行](SOCIAL_PRACTICES.md)を、多数の職業・身分・文化へ拡張するための設計。以下のJSONは**形式の例**であり、確定スキーマでも読み込み可能な既存データでもない。

人格ブロックとランナーの受渡しは[v2の訪問例](AGENT_INTERFACES_v2.md#一つの訪問を両方の仕組みで追う)に示す。ルーティンデータは人格の代わりに判断せず、人格が選んだ方法を実在の担当者の仕事へ展開する。

## 基本方針

多くの行動は、単発の「行為選択」ではなく、**場面を見つけ、既知のルーティンを起動し、人と仕事を配置し、結果に応じて次のルーティンを起動する**連続として扱う。農民の一日、君主の訪問、伝令の配送、書記の文書作成、兵士の警護は、粒度こそ違っても同じ制御の型で表せる。慣行はその中でも社会的に共有され、役割や礼節の期待を含むルーティンである。個人の空腹による食事のような習慣も同じランナーに乗せ得るが、対人約束と同一視しない。

```mermaid
flowchart LR
  C[コンテンツ: 文化・職業・組織・場面・ルーティン] --> L[検証と版固定]
  L --> R[適用可能なルーティンを本人の知識から選ぶ]
  S[届いた刺激・本人が知る状況・意図] --> R
  R --> I[ルーティンのインスタンス<br/>役割・Task・依存・期限]
  I --> P[担当人物の引受・実行]
  P --> E[simのプリミティブ効果・Event]
  E --> U[進捗更新・失敗分岐・次の場面]
  U --> R
```

データが定めるのは「いつ使うか」「誰にどの役を求めるか」「どの仕事をどの順で行うか」「失敗したらどの既定手順に移るか」。プログラムが定めるのは型付き行為の権限・時間・位置・資産・戦闘等の真の効果、配送と知覚、因果Event、保存と再現性である。JSONの任意スクリプトに世界状態を書き換えさせない。

## プランナーが編集する単位

| 定義 | 例 | 保存するもの |
| --- | --- | --- |
| 場面 (`Situation`) | 公式訪問、税通知を受けた、勤務日の開始 | 本人が知る情報に対する版付き判定条件と意味。相手文化では別の場面に見えてよい |
| ルーティン (`Routine`) | 護衛付き訪問、農作業日課、伝令配送 | トリガー、役割枠、Task、順序、期限、既定の例外経路 |
| 役割・職業 (`Role`/`Occupation`) | 君主、書記、護衛、農民 | 資格、職務の既定ルーティン、通常の引受規則。人物IDとは別の共有定義 |
| 文化・組織 (`Repertoire`) | 宮廷の礼法、地域の互助、市の商慣行 | 知られた場面・ルーティンの参照、優先傾向、例外。人物の学習・従属状態とは別 |
| シナリオ | 峠の通行権、人口配置、初期役職 | 採用するコンテンツ束の版、初期資源、勝敗条件、seed |
| 効果プリミティブ (`Capability`) | `deliver`, `travel`, `work_shift`, `transfer`, `meet` | simが実装する引数・権限・費用・結果Event。データは参照だけする |

`Routine` は場面と意図から起動しても、定期的な仕事から起動してもよい。家臣への招待状は「公式訪問」の子Taskから「文書作成」「配送」のルーティンを呼び出せる。出力は人物IDのあるTask/ActionAttemptであり、各人が自分の判断・職務規則から引受・拒否・中断できる。慣行を読み込んだだけで護衛が瞬間的に同行したことにはならない。

共通ランナーは適用可能な定義を探して進捗を管理する。どれを採るかは本人の人格判断またはその人物が従う既定の習慣による。ランナーが全員へ同じ文化行動を強制しない。文化・組織の定義は共有し、個人がそれを知っているか、従うか、例外を選ぶかは人物の状態と判断に残す。

## 公式訪問のデータ例

```json
{
  "id": "court.formal_visit",
  "version": 1,
  "trigger": { "situation": "visit_requested", "intent": "meet_person" },
  "appliesWhen": [{ "fact": "self.role", "op": "has", "value": "ruler" }],
  "roles": [
    { "slot": "visitor", "bind": "self" },
    { "slot": "host", "bind": "intent.target" },
    { "slot": "scribe", "select": "court_scribe", "required": true },
    { "slot": "courier", "select": "available_courier", "required": true },
    { "slot": "guard", "select": "available_guard", "required": true, "count": 2 }
  ],
  "steps": [
    { "id": "prepare", "assignee": "scribe", "capability": "prepare_message" },
    { "id": "deliver", "assignee": "courier", "capability": "deliver_message", "after": ["prepare"] },
    { "id": "assemble", "assignee": "guard", "capability": "assemble_escort", "after": ["prepare"] },
    { "id": "travel", "assignee": "visitor", "capability": "travel_with_escort", "after": ["deliver", "assemble"] },
    { "id": "meet", "assignee": "visitor", "capability": "hold_audience", "after": ["travel"] }
  ],
  "onUnavailable": ["find_substitute", "ask_visitor_to_delay_or_go_alone"]
}
```

これは人数・名称を後で調整できる**一つの文化・宮廷の方法**であり、全文化の普遍規則ではない。`guard`枠に割り当てられるのは実在の人物だけ。二人が集合できない場合に自動で護衛を捏造しない。`go_alone`は君主が再判断する選択肢で、慣行違反の評価や賊の実際の襲撃は別の規則で処理する。相手は別文化のルーティンでこの訪問団を「礼にかなう」または「威圧的」と認識してよい。

## 職業を追加する場合の境界

既存プリミティブの組合せで表せる職業は、職業定義とルーティンデータの追加で扱う。たとえば新しい「陶工」が既存の`work_shift`、材料の受取、商品の引渡しを組み合わせるなら、職務・生産レシピ・勤務ルーティンをデータに置ける。陶器という新しい在庫種や窯の燃焼という新しい世界効果を導入する場合は、在庫型・所有権・効果・保存則・UIのコードとテストも必要になる。**データ駆動は未知の世界法則までJSONだけで作れるという意味ではない。**

拡張を三段に分ける。

1. **データのみ:** 既存の場面判定・役割選択・行為プリミティブを組み合わせ、新しい職業、礼法、仕事の順序、文化差を追加する。
2. **小さな能力追加:** 新しい安全な判定子や役割選択器をコードに登録し、その型と利用可能な情報を検証してからデータで参照する。
3. **世界法則の追加:** 新資源・戦闘効果・疾病・契約の新しい履行効果などはsimの効果と不変条件を実装し、データはそれを設定する。

個別職業名を`if (job === ...)`で増やす設計を避ける一方、効果プリミティブのコードは小さく明示的に保つ。大量のルーティンを足しても1人に全件照合しないよう、トリガー/場面/役割で索引化し、日課は日次単位で処理する。

## データの安全性と再現性

- コンテンツ読込時にIDと版の一意性、参照先、各能力の引数型、役割枠、Task依存の循環、到達不能Step、期限と分岐を検証する。子ルーティン呼出しには深さ・件数の上限を置く。
- `appliesWhen` は人物が知る情報だけを読む。真の可否は実行時にsimが別途判定する。相手の秘密や未着の伝令を条件から漏らさない。
- 複数ルーティンが競合した場合の選択順は、場面の特異度、文化・組織の優先順位、人物の既知情報、安定したID順などを版付きで定義し、採用/省略したルーティンIDを記録する。
- 進行中の`RoutineInstance`にはコンテンツID/版、担当人物ID、Task状態、原因Event、次回判断時刻を保存する。保存後にコンテンツが変わっても、移行か旧版参照なしに進行中の仕事を読み替えない。
- ルーティンが同じ日に大量起動しても、日次会計は既存の集約帳票を使える。個人のTaskと結果はIDで追える必要があるが、全仕訳や全認識を長文Eventとして複製するとは限らない。保存量・処理時間は実装後に測る。

## 現行実装との距離

`packages/content/scenario.json` は人口・価格・賃金・戦闘係数・道路を持つが、職業・文化・面談・伝令のルーティンは定義しない。`packages/content/validate.ts` はシナリオIDと道路の地名を固定列挙する。職業の初期割当、宮廷役、農業/加工の生産、伝令の選任、面談手順は `generate.ts`、`economy.ts`、`diplomacy.ts` 等の分岐にある。したがって現行は**係数と地形の一部がデータ駆動**であり、社会的行動はまだデータ駆動ではない。

移行の最小単位は、まず現行の「招待状作成→配送→面談」を、同じ結果Eventを作る版付きルーティン定義で表現できるか紙上で照合すること。その後に護衛、日次就労、異文化の訪問手順へ広げる。ゲームコードの実装、コンテンツ読込、型検査、受入テストは未着手。
