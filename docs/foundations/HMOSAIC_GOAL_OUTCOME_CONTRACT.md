## 行為・行程・成果・価値を分ける

| 層 | 判定すること | それだけでは判定できないこと |
|---|---|---|
| 意図の結果 | 世界が受理／完了／失敗／拒否／中断したか | 本人の目的が達成されたか |
| 行程の進行 | 段階・分岐を進め、次の試行が残っているか | 栄養確保や必要な身体回復を得たか |
| 目的の成果 | 採用時に指定した必要量・対象・期限に対し、本人がどこまで観測できたか | 生存確率、数値的な親利得、各子の寄与 |
| 選択の価値 | 同じ期間で生存・不快・備蓄をどう比較するか | 選んだ後に世界で実現することの保証 |

現行の `Goal.completion = arrival / absorption`、`Goal.status = completed` は接続試作の行程終了規則である。回復改訂版でも `arrival` のままで、最後の休息結果まで進めて終了する。`ControlFeedback.payload.achieved` は局所行為の `completed` から作る。これらを食品確保・回復の成果として再解釈しない。

## 採用時に固定する成果の条件

親は目的を採用するとき、以下を提案する。検証した状態所有者が保存し、比較・追跡が同じ条件を参照する。完了判定器は証拠から結果を返し、世界やモデル状態へ書き込まない。

| 項目 | 保存する意味 |
|---|---|
| 識別 | 人物、目的ID、目的改訂、行程版、判定器IDと版 |
| 対象 | 食品の取得・摂食・吸収、活動疲労の回復、睡眠回復を区別する。複合の親は必要な成果を列挙する |
| 必要量 | 取得量・食事回数、疲労の到達目標、必要な有効睡眠量など。単位と観測可能性を持つ。親が必要に応じて提案し、実装共通部へ固定閾値を置かない |
| 時間窓 | 採用分、達成期限、結果を追跡する期限。行程を改訂したときの対応規則は運用契約を継承する |
| 根拠 | 採用時の主観観察、必要を見積もったモデルと改訂、判定に必要な観測項目 |
| 比較 | 評価基準と評価期間の参照。成果の期限と候補を比較する期間は別に保存する |

必要量・期限を変更するなら目的改訂を上げる。子の順序・引数だけを変える場合は行程版を上げる。過去の予測・結果は元の条件へ戻し、達成できるまで事後的に目標を下げて成功へ書き換えない。必要量の生成式・具体値は生活の選択方式と併せて未決である。

## 本人の観測から何を確認できるか

| 目的・段階 | 使える証拠 | 完了としない例 |
|---|---|---|
| 食品への到着 | 本人の現在地と対応する移動結果 | 食品を見た／目的地に着いたが、取得していない |
| 食品取得 | 対応する取得・採集・購入の成功結果と、本人の所持品・ロット・可食量の観測 | 売却だけ、他者の在庫、所有権だけ、遠隔の保管品を携帯食へ数えること |
| 摂食 | 対応する `eat` の成功結果。取得とは別の段階 | 食品を持つだけ、食事の拒否、穀物を直接食べたとする推定 |
| 吸収 | 食事に対応した追跡と `digesting` の真→偽、栄養需要の観測。直接観測でなく推定として保存 | 別の食事が重なった場合を一つの食事の確定成果とすること。本人に見えない栄養備蓄・吸収量の参照 |
| 活動疲労の回復 | 対応する休息／睡眠の前後の `fatigue` と経過時間。目標への到達と、正の変化量を区別して記録 | 帰宅だけ、休息を提案しただけ、休息結果は出たが必要な回復を観測できない場合 |
| 睡眠回復 | 本人へ届く `experience.sleep.actualHours`、入眠待ち時間、起床後の `sleepDeficit` 等 | 入眠待ちや短い休息を有効睡眠に数えること、眠気だけから睡眠不足の解消を断定すること |

証拠の元になる現行型は [ActionObservation / ActionExecution](../../packages/ai/action-learning.ts)。v25アダプターの現在の `Evidence` には睡眠の詳細をまだ渡していない。睡眠判定の接続には型と投影の版が必要であり、世界の睡眠法則を変える理由にはしない。

採用する成果状態は `pending`（待つ）、`satisfied`（必要条件を確認）、`not-satisfied`（有効な観測が必要条件を満たさない）、`unknown`（欠測・識別不能・未対応）を区別する。直接観測／推定という証拠の種類、観測量、証拠ID、判定分を結果に添える。曖昧な吸収は `unknown` にして理由 `ambiguous` を保持する。拒否・中断・期限・置換・保持上限は運用契約の終了理由として別に記録し、期限切れを自動的に数値的失敗へ変換しない。

子の局所予測は有効な実結果があれば更新できる。親の成果が不明でも子の予測まで全て負の教師にせず、親利得・制御・構成の更新は必要な証拠と採用済みの更新則がそろうまで行わない。

## 比較期間と計算法の採用条件

形式仕様の生存・累積不快・期間末備蓄のベクトルを主案とする。候補を比べる判断では同じ開始分と期間 `H` を使い、行程が早く終わった候補にも残りの期間の状態予測が必要となる。売却・購入・吸収を同じ便益として重複加算しない。

`H=24時間`は主案の仮値で、未採用。短い行程の最終状態だけで期間全体を比較しない。期間内の身体・吸収・供給の依存を宣言できない場合は未知を残し、点予測や独立と決め付けない。未知候補を最大集合に残す形式仕様と、未評価候補を選択対象から外す現行試作の差を、接続時に明示する。

採用前の計測項目は、予測と実入力の差、吸収までの時間、欠測と曖昧の数、未評価・予備応答の理由、異なる期間での順位変化、生存・不快・備蓄の各推定と実結果である。身体の実測は世界監査、本人の判断は主観入力から別に再計算する。重み40の仮評価は今回維持し、生存比較の実装とはしない。

## 今回実装した状態操作

| 所有者・操作 | 不変条件 | 実装 |
|---|---|---|
| `ExecutionState.current / nextStep / select / finishPlan` | 目的の期限・行程進行・採用と再開・旧終了規則を一か所で扱う。runtimeは目的を直接変更しない | [state.ts](../../packages/ai/hierarchy/state.ts)、[runtime.ts](../../packages/ai/hierarchy/runtime.ts) |
| `ExecutionState`の読取・更新 | 読取結果は複写して再帰的に凍結。更新対象はID・目的改訂・行程版を所有者が照合し、古い行程からの更新と終了済み目的の再開を拒否する | 同上。改訂後は返された新しいスナップショットを使う |
| `TrackingLedger.settlePlan` | 実行状態の終了は実行所有者へ依頼し、追跡の終了・未計測利得は台帳側で扱う | [tracking.ts](../../packages/ai/hierarchy/tracking.ts) |
| `ModelStateStore.apply` | 対象・経験ID・更新元改訂・codecを検査する。適用済み経験の再配送は無変更。未適用で改訂が古ければ確定前に拒否する | [state.ts](../../packages/ai/hierarchy/state.ts) |
| `DecisionHistory.record / fail / retain` | 判断・失敗の追加と保持を所有する。予備応答の出所は記録時に指定する | [history.ts](../../packages/ai/hierarchy/history.ts) |
| `DecisionSession.calls` | モデルへ渡すのは `invoke / refs / take / limit / peak` の凍結した窓口。session本体・可変状態・登録簿・予算オブジェクトを渡さない | [session.ts](../../packages/ai/hierarchy/session.ts) |

学習器は `store.read` で取得した改訂と値から次状態を計算し、その改訂を `apply` へ渡す。診断に使う過去のモデル改訂と、次状態を計算する現在の改訂は別である。改訂違いを現在値への強制上書きや失敗教師へ変換しない。現在は単一判断内の逐次更新で、並行更新・自動再試行は実装しない。

今回の内部再構成は正常な保存入力に対する判断・状態の変更を意図しない。既存二構成の判断再計算とhashで互換を確認する。今後、成果判定を生活の選択や保存状態へ接続する際は新しい構成／ruleset／記録で区別する。

## 呼出し権限と残る境界

モデルへsession本体を渡さず、`DecisionSession.callsFor(modelId)`が呼出し元を固定した窓口を作る。`Definition.calls`に呼出し先（別名可）・役割・契約を宣言し、省略時はモデル呼出しを許可しない。データのポート辺とは別の宣言で、登録簿の`compile`と実呼出しの両方で検査する。予備応答の依存宣言は読込時に拒否する。

| 呼出し元 | 許可する要求名 | 相手の契約 |
|---|---|---|
| `travel-control@1` | `$travel-prediction` | forward / duration-v1 |
| `compose@1`・`compose@2` | `$travel`、`$body` | control / travel-control-v1、forward / body-v1 |
| その他の試作モデル | なし | 行程の子は合成器が検査して呼ぶ |

別名を契約の合う別実装へ差し替えられるが、別名の許可は任意の実モデルIDを呼ぶ許可にはならない。子は自身の許可で実行し、親の許可を継承しない。合成器は行程に書かれた子にも同じ検査を課す。許可検査はキャッシュ・参照追加・相手の予算消費より前に行う。学習器の直接実行にも学習器自身の窓口を渡す。実行器と追跡台帳は信頼された組立て側であり、この制限の外にある。

[input-projections.ts](../../packages/ai/hierarchy/input-projections.ts)へ主観入力の型と投影codecを分離した。移動制御は現在地・荷重・行動・寒さと疲労、仮の親は場所・候補地と仮優先度に使う身体項目、回復親@2は場所・候補地・行動、予備応答は行動・空腹・食数に限定する。合成器は委譲と身体予測に必要な項目だけを受ける。既存の移動／身体順モデルは従来の専用入力を保つ。登録簿の`project`がcodecで切り出して凍結し、実装へ渡す。

キャッシュは投影後の入力をキーにする。広い入力を持つ実行器と限定入力を持つ合成器から同じ要求が届いても、一度だけ計算して各消費者へ予測参照を残す。順モデルの保存入力・出力と診断codecは従来どおりで、旧二構成の正常な判断・保存JSONを変えない。`projection: subjective-v1`は既存の主観入力系列名として維持し、具体的な項目の制限は各登録の入力codecが担う。投影名から処理を動的解決する機構ではない。将来、保存する予測入力や計算法を変える際は新しい版を使う。

分析器が閉包から登録簿を参照する診断経路と、共通の予測参照一覧は残る。この仕組みは通常のモデル要求の依存制限であり、未信頼コードの隔離や全情報経路の権限制御ではない。

共通部品は依然として人物のJSONを共有し、`ExecutionState`は追跡の作成・改訂、`ModelStateStore`はスナップショットの参照状態にも触れる。外部置換時の選択履歴の変更も実行所有者に残る。全ての状態所有を完成したとはしない。現在の境界を保ったまま、追跡への依頼と履歴への通知へ分ける余地がある。

## 検証と次の接続

[所有と改訂の対照](../../tests/hierarchy-ownership-v25.test.ts)では、読取結果を書き換えられないこと、古い行程・学習改訂を拒否すること、JSON再開後の更新重複防止、遅延結果と未計測利得の区別、モデルへの参照漏れ、既存回復版217判断のJSON一致と記録hashを確認する。これらは抽象化と互換性の検査であり、上記の生活成果判定の実装テストではない。

呼出し許可とモデル別入力は上記の範囲で実装した。次は追跡・診断の境界を整理し、成果判定器と食品・睡眠の証拠を別版で接続する。取得・摂食・吸収を通す成立例と、枯渇・競合・期限・曖昧を持つ不成立例を実世界で測る。生活選択・制御更新・構成変更の採用は別に判断し、既知の栄養死の再現を生活成立の合格にしない。
