# E1契約: 食料を人が運び、市場で受け渡す

状態: **独立した20人fixtureの食料流通を実装・検証済み**。現行本編への接続、汎用ルーティン展開、人格v2、長期の資金循環、性能測定は未実装。[E0基準](ECONOMY_E0_BASELINE.md)と[実装前監査](ECONOMY_IMPLEMENTATION_READINESS.md)を受け、E1で必要な七項目を決めた。価格形成・賃金循環・装備はE2以降の課題であり、この契約の達成結果に含めない。

## 1. 在庫と通貨の正本

E1の新方式では**食料ロットだけが食料の正本**。`FoodLot {id, ownerId, place, quantity, reserved, causeEventId}`を世界に保存する。`place`は`farm`、`market`、`house:<householdId>`、`cargo:<shipmentId>`、`carried:<personId>`の識別子。`ownerId`は事業または世帯のIDで、積載中も所有者が変わらない。ロットの分割には新IDと元ロットの原因IDを付け、合計量を変えない。`reserved`は`0..quantity`で、同じ1単位を二つの依頼に約束できない。

通貨は新世界の所有者別`wallets[id]`を正本とする。旧本編の`accounts[id].money`とは混用しない。`MoneyHold {id, accountId, amount, orderId}`は支払可能額から差し引く**拘束**で、通貨を別口座へ複製しない。受領時に同一のsim遷移で買主→事業へ通貨を移し、拘束を解除する。失敗・期限切れは拘束だけを解除する。

E1用世界は旧`accounts`を持たず、食料合計をロットから数える。保存則は`Σwallets = initialMoney`、`Σlots.quantity = initialFood + producedFood - consumedFood - explicitLossFood`。市場や荷車の食料を重複加算しない。旧世界ではロットを持たず、従来どおり`accounts.food`を正本とする。**同一世界内で新旧の食料経路を混用しない**。旧ゲームの軍用`Shipment`や既存セーブをE1で推測変換しない。

## 2. 輸送と購入を分けた状態機械

前の監査にあった`requested→stock_reserved→in_transit→market_ready→sale_reserved→settled`は、一便と複数の購入注文を一本につないでいた。E1では次の二つを別ID・別状態にする。

| 対象 | 状態と遷移 | 実在する効果 |
| --- | --- | --- |
| `Replenishment`/`Shipment` | `requested → assigned → loaded → in_transit → delivered`、任意の途中から`failed/cancelled` | 売り手が不足を知らせ、運搬人が引受。農場の事業所有ロットを予約/積載し、時間を使って市場へ移す。**受領して初めて市場在庫**になる。失敗時は貨物の最後の実在位置に戻し、担い手不在で瞬間返送しない |
| `PurchaseOrder` | `requested → sale_reserved → settled`、または`expired/cancelled` | 世帯の買物係が注文。市場に実際にある事業所有ロットと世帯の支払可能額を同時に拘束し、買物係が受領した時だけ食料所有権と通貨を同時移転。期限切れなら両方の拘束を解除する |

出荷数量は一便の容量まで。E1では積載済み便の部分配送をしない。品物が一部しかないときは初めから別便とする。世帯の注文も初版では全量または不成立とし、部分購入は小さい注文へ分割して表す。売り手が注文を受けただけ、運搬人が担当になっただけ、商品が道中にあるだけでは世帯の食料にも売上にもならない。売主は配送中の損失を負い、損失は原因Eventを伴う明示`loss`で処理する。E1 fixtureでは道路襲撃/腐敗は発生させず、失敗の対照は運搬人不在や買物係の資金不足で作る。

各遷移は`causeEventIds`、Task ID、担当人物ID、時刻、実量を持つEventを残す。`settled`と資産移転は一つのsim操作として原子的に確定する。同時注文は利用可能な市場ロットと`money - holds`だけを見て、日付で回転する安定世帯ID順に処理する。最初の受入fixtureでは4世帯とも5食を買える条件を用意し、配分規則が現れる不足ケースも別に試す。

## 3. 人物の時間と場所

全Taskは`[startMinute,endMinute)`の半開区間と開始/終了場所を持ち、`start < end`。人物ごとの予約一覧を唯一の占有正本とし、勤務・買物・荷積み/移動・宮廷仕事・軍務を重複させない。E1世界は軍務/宮廷Taskを生成しないが、予約の種類は後から共有できるよう型付きにする。移動中の人物は`Person.location`の単一拠点だけで「目的地に到着済み」としない。経路と到着予定を持ち、到着Eventで位置を変える。睡眠・排泄の世界効果はまだ追加しない。

予約は引受時に空きと経路を検証してから作る。実行時に負傷、拒否、期限切れ、道の不通が判明したら失敗Eventと拘束解除を行い、空白時間を成功扱いしない。時刻が同じ場合は到着→Task完了→掲示/注文→新規予約の順に処理し、同時刻に無限にTaskを再起動しない。乱数や壁時計ではなく時刻・人物ID・Task IDで安定順を決める。

## 4. 何を誰が知り、依頼するか

各世帯の買物係、協同事業の市売り手、農場の作業責任者、運搬人は実在の人物IDに結びつく。買物係は世帯の委任と自宅在庫/予算を知って注文を出す。市場にいる売り手は掲示済み注文と**到着した**在庫を知り、農場の実在庫や遠方の人の秘密は知らない。農場の責任者は事前の作付け/勤務計画を知り、売り手の当日変更は人が運んだ依頼が到着した場合だけ知る。運搬人が欠勤しても、既知の定例勤務に従う農民は働けるので、農場に食料が残る。

同じ市場拠点内の掲示は次の15分境界で関係者へ届く。農場への変更依頼は運搬人が往路で届け、到着まで本人の認識へ混ぜない。E1 fixtureの通常生産は予め知られた3日周期の定例勤務であり、毎朝の遠隔情報を必須にしない。制度は注文の照合や期限切れを機械的に処理してよいが、発注・引受・積載・販売/受取には担当人物のTask/Eventが要る。

## 5. E1で使う人格・ルーティン境界

E1は[人格v2](AGENT_INTERFACES_v2.md)全体の実装を待たず、同じ意味の最小経路を固定する。

```text
known stimulus + routineRef(id,version) + role/availability
  → TaskOffer(id,assigneeId,window,causeEventIds)
  → TaskAnswer(accept | refuse | defer, reasonRef)
  → ActionAttempt(work_shift | carry_food | market_sale | buy_food | eat_food)
  → sim Event(success | failure, actual time/asset delta)
  → 知り得た人だけへ結果を配送
```

ルール実装は通常職務を受け、欠勤・資金不足・時間重複なら拒否または失敗にする。ルーティンは版付きデータで役割・時間窓・Step依存・数量上限を定義し、simの資産操作を任意スクリプトとして埋め込まない。本人の認識には利用できる掲示と依頼だけを渡す。複数Taskは共通ランナーが一つのルーティンから展開できるが、各担当者の`TaskAnswer`は独立。v2の未解釈刺激や主観更新の原子性は引き続き別の設計課題として残す。

E1で読み込むルーティン定義の必須項目は`id`、`version`、`trigger`（時刻/到着済み掲示/在庫到着）、`roleSlots`、依存関係を持つ`steps`（担当枠・型付きcapability・時間窓・数量上限）、`onUnavailable`である。`work_shift`、`carry_food`、`market_sale`、`buy_food`、`eat_food`だけをE1のcapabilityとして登録する。未登録の能力、重複ID、循環するStep、負の数量、存在しない役割枠、時間窓の逆転は読込時に拒否する。具体的な職務係数と3日周期はfixtureコンテンツに置き、任意のJSON式から世界状態を書き換えることは許さない。Rule/NN/LLM/人間という区別はこの入力・出力契約の外にあり、人格の実装を差し替えてもTaskとsim効果の意味を保つ。

## 6. 旧処理とセーブの切替

E1は**世界単位の排他的なモード**で作る。既存の「峠と収穫」は`legacy`のままで、`newGame`・旧セーブ・既存90日経路の挙動を変えない。独立した20人のfixture世界だけ`local_food_v1`として開始し、旧`dailyEconomy`の生産・食事・給与を一切呼ばない。E1 fixtureは初期通貨を使う物理流通検証で、無期限の家計資金循環を保証しない。賃金・利益分配はE2で接続する。

新モードの保存にはモード、ロット、予約、輸送、購入注文、人物別の時区間Task、掲示の到達状態、版付きルーティンIDとコンテンツハッシュを含める。現行`schemaVersion:1`/engine `0.2.0`のセーブを受け取っても自動で所在地を作らない。E1の新モードは`schemaVersion:2`、`economicMode:"local_food_v1"`とし、旧版は従来経路で読み込む。E2/E3で本編を移行するときに旧口座→ロットの場所別移行表を別に設計する。`save→load→同じCommandと進行`およびseedからの再実行で同じEvent・資産・最終ハッシュを要求する。

## 7. 20人fixtureの場所・人・時刻

農場と市場は2kmの道路で結ぶ。4世帯は市場拠点に住み、各世帯5人。人物20人の配置は次のとおり。農家・市売り手・運搬人・買物係は別の人物であり、各人に固有IDを付ける。

| 世帯 | 農家 | 他の職務 | 買物係 | 扶養家族 | 初期資金/食料 |
| --- | --- | --- | --- | --- | --- |
| H0 | F0, F1 | なし | B0 | D0, D1 | 40通貨/0食 |
| H1 | F2, F3 | なし | B1 | D2, D3 | 40通貨/0食 |
| H2 | F4, F5 | 売り手S | B2 | D4 | 40通貨/0食 |
| H3 | F6 | 運搬人C | B3 | D5, D6 | 40通貨/0食 |

食料価格2、各人1食/日。協同事業の初期通貨と食料は0、農場の勤務は日1/2に7人、日3にF6を休ませて6人。完了した農家勤務1人あたり3食を農場の事業ロットに生産する。市場の販売目標は4世帯×5=20食/日。運搬人は最大21食を一便で運ぶ。日1/2は21食ずつ市場へ運んで終値在庫1/2、日3は18食を運び、在庫2と合わせて20食を販売する。3日合計は生産60、購入/食事60、事業・市場残高0。世帯初期通貨は3日分を賄い、売上120は協同事業に移る。**この120通貨はまだ賃金として世帯へ戻らない**ので、3日以上の自律経済が成立したとは言わない。

| 時刻（各日） | 人物のTask・物理効果 |
| --- | --- |
| 05:00–05:15 | B0〜B3が各5食の買物注文を掲示。Sは05:15以降に読める |
| 05:30–06:00 | F0〜当日勤務の農家が市場拠点から農場へ徒歩移動（4km/h）。Sが当日入荷依頼を掲示し、Cへ割当 |
| 06:00–07:00 | Cが市場から農場へ荷車で移動（2km/h）。依頼の変更があれば07:00に農場へ届く |
| 07:00–12:00 | 農家が勤務。完了時に農場で事業所有の食料を生産。Cは農場で集荷を待つ |
| 12:00–12:30 | Cが最大21食を積載。農家は12:00–12:30に徒歩帰宅 |
| 12:30–13:30 | Cが市場へ戻る。食料の所有者は事業のまま、所在地は荷車 |
| 13:30–14:00 | Cが市場で荷下ろし。受領Event後に市場在庫になる |
| 14:00–15:00 | SがB0〜B3と15分ずつ受渡し、現物と代金を原子的に清算。買物係の市場内移動と購入は同じ15分枠で扱う |
| 18:00–19:00 | 世帯の現物から各人が1食を消費。足りなければ人物別に欠食Event |

睡眠や排泄はE1の時間表にまだ入れない。勤務のない時間を「寝た」と記録しない。買物係は市場と同じ拠点に住むが、15分の移動/受渡し枠を要する。道路が塞がる、Cがいない、Bの資金が足りない、農家が欠勤する場合はその人物と在庫の実状態に応じて別の結果になる。

## 受入の最小対照

1. 基準3日: 上の60食と120通貨の移動、20人×3日の食事、担当者の時間非重複、全Eventの原因、保存/再開・再実行が一致する。
2. Cが日2に欠勤: 農場勤務は続いて食料が農場に残り、市場の世帯は初日在庫1食以上を勝手に利用できず、購入/食事が基準から減る。代役がいる設定なら代役IDと時間を記録する。
3. H0の初期通貨を0にする: B0の注文は支払不能になり、H0へ無償の食料が移らない。他世帯の注文・食事には影響を限定する。
4. F6が日2に欠勤: その日の生産は基準より3食減る。受渡しが不足した世帯と、残った市場在庫を追える。
5. 同一世帯が同じ通貨と現物へ二つの注文を出す: 予約で二重清算を防ぎ、取消/期限切れなら拘束を解除する。

この契約の値はE1の検証用仮決定であり、既存の本編世界を2km道路・協同事業に書き換える指示ではない。

## 実装差分（2026-09-26）

`packages/sim/local-economy.ts`の独立世界でロット・資金拘束・配送・購入・人物別Task・因果Event・保存再開を動かした。`npm run economy:e1 -- baseline`と三つの対照ケースで観察できる。`packages/content/economy-e1.json`は役割、係数、時刻、版付きcapabilityを定義し、読込時に矛盾を拒否する。基準3日で60食生産/消費、配送21/21/18、世帯から事業へ120通貨が移る。全員の食事EventとTask、購入と配送の原因を保存する。

この初版の時刻相・役割展開・効果ハンドラはコードに固定されている。上記第5節の`roleSlots`・依存Step・`onUnavailable`を備えた共通ルーティンランナー、人格によるTaskAnswer、認識の配送状態はまだない。農場への依頼到着Eventは記録するが、農場責任者の独立した認識モデルと依頼変更による作業変更はない。E1の「食料が実際に人を経て循環する」検証は満たしたが、第3〜5節の汎用契約を完了したという意味ではない。旧本編への切替は未接続で、専用のschemaVersion 2世界だけが動作する。

## 空間デバッグの追加（2026-09-26）

`map`に町、農場、市場、各世帯の家の矩形を定義した。家は`house:<householdId>`、人物はその世帯の所属を持つ。農民・売り手・運搬人・買物係は`Journey {from,to,depart,arrive}`で移動中と到着後を区別する。購入品は買物係の`carried:<personId>`を経て家に置き、家にある現物だけを食事で消費する。生産・運搬・清算・持ち帰り・食事をEventでたどれる。地図の矩形座標はデバッグ表示用の相対位置であり、道路距離2kmと市街の15分移動は時間表で定義する。建物内の細かな移動、衝突、道路閉塞は扱わない。可視化は`/?e1=debug`で開き、4つの対照ケースを時刻ごとに比較できる。本編90日世界の家配置を作ったという意味ではない。
