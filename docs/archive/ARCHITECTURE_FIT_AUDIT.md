# 現行実装と認知・行動インターフェース v2 の適合調査

調査日: 2026-09-25。対象: `packages/` と既存テスト。**コード変更なし。** 判定はv2への移行可能性であり、v2が実装済みという意味ではない。

## 判定

**土台は利用できるが、現状をそのまま各Portへ代入することはできない。** 人物ID、保存状態、配送、行為の型、因果Event、資産不変条件は再利用できる。一方、刺激の受信・解釈・動機・判断が sim 内で混ざっており、文化は主に行動スコアと定型台詞にしか作用しない。v2の「文化と状況によって認識そのものが変わる」は現在成立していない。

| v2の境界 | 対応する現行コード | 適合判定・必要な整理 |
| --- | --- | --- |
| 人物固有の持続状態 | `contracts.Person` のID、culture、values、trust、memories、beliefs。`generate` が全員に割当 | **再利用可**。人格ID・改訂・実装版は未保存。世界の身体/役職状態と主観状態を二重管理せず所有者を決める |
| 到達・可視性 | `Message`、`send`、`arrivals`、Eventの`witnesses`、`report`/`receiveReport` | **部分適合**。人の伝令と遅延はあるが、刺激の独立ID・内容・配送履歴が足りない。届いた報告を直ちに確信度1の`beliefs`へ写す |
| 文化・状況による認識 | `culture`、`knownTax`、`trust`、`ActorObservation` | **不適合**。`PerceptionPort`相当がなく、分類・原因帰属・疑いを人物別に生成しない。`policyResponse`は解釈後の目的を引数で受ける |
| 動機づけ | `policyResponse`の規範/信用/報酬/負担/空腹、面談承諾条件、仕事/約束 | **部分適合**。ルール素材はあるが単一スコアや個別ifに融合し、必要・仕事・対人約束の衝突を表す結果がない |
| 判断 | `policyResponse`、`OrdinaryPlanner`、`receiveInvitation`、`receiveOrder`、外交回答 | **部分適合**。型付き行動へ写せるが、住民の日課は判断ではなく直接の日次更新。通常Plannerは敵君主だけ。判断草案、根拠、人格更新の共通境界がない |
| 行為・結果 | `actionSchema`、`submit`、`apply`、Event、`transfer`、`check` | **再利用可だが改修要**。simが資産と実行可否を持つ点は合う。判断からCommandへのGateway、知り得た結果を戻す経路は未分離 |
| 全員の追跡・再現 | `Activity`、`debugSnapshot`、`save/load`、`replay` | **部分適合**。実行Eventと日次活動は見えるが、全員の刺激→解釈→動機→提案は未記録。現行ルールAIの再実行は成功するが、別実装の応答ログ再生は未対応 |

## 重要な具体例

- 税通知: `engine.arrivals` は配送直後に `knownTax` を更新し、`policyResponse`を呼んで納税まで行う。文化は `policyResponse` の規範係数にだけ入る。同じ通知を「共同負担」「約束違反」と解釈し分ける経路はない。`SET_TAX`時には世界の税率が先に変わり、本人には後で届く構造自体は利用できる。
- 報告と信用: `core.event` は目撃者へEvent本文を確信度1の`beliefs`として保存し、`receiveReport`も原Eventの本文を確信度1で保存する。報告の内容、配送されたという事実、本人の解釈を分ける必要がある。`observe`は既知Eventを使う一方、同勢力の人物一覧や国庫など一部を現在のWorldから直接投影しているため、v2の人物用入力としてそのまま使わない。
- 約束・命令・面談: 約束の履行は資産移動を伴いEventが残る。伝令・書記・面談者も人物IDで追える。ただし約束の到着で`active`と「受諾」に自動遷移し、受益者の判断はない。面談承諾と軍命令への反応はsimの個別if/スコアで決まり、共通の判断経路を通らない。外交の受け手は届いた文面ではなくWorld内の`Offer`を参照して判断する。
- 日課とデバッグ: `dailyEconomy` は仕事・給与・消費を直接更新し、その後で全員の`Activity`を作る。`Activity`は有用な行動記録だが、選択や仕事の発生原因ではない。`debugSnapshot`は活動・当事者Event・未着を含む現在のMessageを閲覧できるが、既に配達されたMessage本文や認識・動機の履歴はない。

## 移行前に解くべき設計論点

1. **刺激と主観の所有権**: Event、Message、Report、beliefsをどの境界で分けるか。配送済み本文を保存し、同じEventから人物別に異なる刺激を作る。既存の`beliefs`を二重保存しない。
2. **文化の意味**: 現行3文化・4価値軸を維持した最小例で、税・面談・約束の同一刺激を違って分類する規則を先に定義する。単に現行スコアの各項を`MotivationalPressure`へ移すだけでは認識ブロックの要件を満たさない。
3. **仕事と制度的自動処理の線引き**: 住民が仕事を選ぶ/引き受ける行為と、既に働いた後の生産量・賃金・食事・税の会計規則を分ける。全員に毎分推論を要求せず、日次/到着/割込みで判断窓を開く。
4. **世界効果の位置**: 現行の `actionSchema` とsimの検証を残し、人物の応答は型付き試行として渡す。約束の受諾、命令への応答、外交回答を共通経路へ移しても、資産・人口・戦果はsimのみが確定する。
5. **保存・再生**: 人格改訂、ブロック出力、配送済み刺激、採用した提案のログと旧セーブ移行を設計する。現行のseed＋外部Command再実行の成功は、非決定的実装の再現性を証明しない。

着手順は、(a) 税通知1件の「配送→文化と状況による認識→動機→返答」の対照fixture、(b) 報告と主観状態の分離、(c) 既存の命令・面談・仕事の段階移行、(d) 90日シナリオ回帰が妥当。これは実装計画の提案であり、着手はしていない。

今回の確認: Linux版Nodeで `npm run typecheck` 成功、`npm test` は5ファイル・28件成功。これらは**現行実装**の検証であり、v2契約の検証ではない。最初に環境のPATHがWindows版npmを指し失敗したため、Linux版Nodeを明示して再実行した。
