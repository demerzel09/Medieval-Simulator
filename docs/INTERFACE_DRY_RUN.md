## 空の実装の意味

空の認識は「何も届かなかった」でも「届いた内容を信じた」でもない。`ReceivedStimulus` を失わず、**新しい解釈を追加しない**という意味に限定する。空の動機は「欲求がない」ではなく、**新しい動機評価を生成しない**という意味にする。既存のルール判断が必要な刺激と人物状態を参照できれば、現在の挙動を保ったまま境界だけ先に試せる。新しい解釈や動機の効果を実装したと主張しない。

## 設計側で露出した問題と最小修正候補

1. **空の認識で情報が消える。** v2の`PerceptionResult`は`interpretations`と消費IDだけ、`DeliberationInput`はその解釈だけを受ける。現行の`policyResponse`に必要な税の目的・額、軍命令の意図、面談の招待が消える。`PerceptionResult`に未解釈の刺激を参照・閲覧できる欄を残し、判断には結果全体を渡す。「解釈が空」と「刺激が空」は別状態にする。Raw World Eventを渡すのではなく、配送時に秘匿を除いた内容を渡す。
2. **「認識済み」「入力を処理済み」の区別が曖昧。** `consumedStimulusIds` は空実装でも埋めるのか、解釈できた時だけ埋めるのか不明。配達の受領・重複防止と、本人の解釈/記憶更新を別のIDで表す。未解釈の通知が黙って消えたり、毎分再処理されたりしないようにする。
3. **判断の出力語彙が足りない。** `DecisionDraft.proposal` は単一の意図・計画・行為・延期だが、現行PlannerはAction配列を返す。面談の承諾・拒否、外交の反対提案、命令への回答は行為試行とも延期とも限らない。上限付きの0〜複数提案と、相手のTask/提案への型付き応答を候補に加える。空の提案、再判断時刻、順序の意味を定める。既存の`Action`は君主の権限コマンド中心なので、市民の就労・移動・返答を同じ列挙に押し込むとは決めない。
4. **状況の入力は誰の知識か。** `SituatedContext.knownRelations/activeTasks/knownCommitments` はWorldの台帳からそのままコピーすると秘密を漏らす。一方、本人の場所・空腹・任命された職は本人に分かる。本人の身体/制度上の自己状態、届いた他者情報、主観的関係を区別し、由来のない初期設定には生成時の根拠を定義する。`CulturalFrame`も初期の3文化を参照可能な版付き意味へ写せればよく、最初から大きな規範DSLを必須にしない。
5. **いつ誰を呼ぶかがPort契約外。** 住民1,000人の毎分全Port実行は現行方式とも合わない。伝令の到着、日次、負傷、役職変更、約束期限などを判断窓の原因にし、処理順・同時刻の優先順・1窓での提案上限を定める。刺激なしの習慣的日課も許す。空実装の結果により再判断が永久循環しない条件が必要。
6. **各ブロックの状態更新とGatewayの「原子的採用」が矛盾する。** v2は認識更新を順に適用して後続Portへ渡す一方、最後に草案と状態を原子的に採用する。途中で判断が不正/失敗した場合、配送済み通知と認識更新を巻き戻すのか不明。1回の判断窓の中で仮状態を渡し、採用時に一括確定する、または受信/認識だけを独立確定するなど、トランザクション境界を決める必要がある。
7. **複合実装に中間出力を毎回要求すると逆に方式を縛る。** v2は「複数ブロックを一体で計算してよい」と述べつつ、全ブロックの結果記録を義務にする。人間やNNが認識・動機を独立に明示しない場合、空欄を捏造することになる。最低限必要な監査情報（届いた刺激、最終提案、採否、世界Event）と、任意の解釈・動機診断を分ける。意味のある中間結果が出せる実装だけを各Portに分ける。
8. **Eventと配送内容の形が足りない。** 現行の`Report`は原Eventを確信度1で複製し、`Message`は配達後キューから消える。今後は「世界のEvent」「相手が実際に送った文面」「配送Event」「本人が受け取った刺激」「本人の解釈」を別IDで追う必要がある。ただし現行ログ全件に長文の認識結果を追加する前に、保存量と検索性能を測る。

## 実装側の課題（設計を直しても残る）

- `policyResponse`、面談承諾、外交回答、軍命令応答は別の場所にある。同じ人物入力から旧結果を出す互換アダプターを作るには、必要な刺激を各経路から正規化し、simの資産更新と切り離す必要がある。
- `core.event` と `receiveReport` が受信と信念確定を同時に行う。空認識で旧挙動を保つ期間はこの旧処理を互換層に隔離し、解釈したふりをしない。
- `observe` の同勢力人物一覧、国庫、進行中Offer等にはWorld直読がある。v2の全人物用入力として流用せず、本人が知り得る由来と鮮度を持つ投影を作る。
- `Activity` は行動決定の証拠ではなく日次処理後の記録。全員の仕事を「選んだ行動」として見せるには、既定業務の割当・継続・中断と実際の生産を因果でつなぐ必要がある。
- 現行replayは決定的ルールAIをseedと外部Commandから再実行する。人格改訂、各窓の入力/採用応答、非決定的な実装の録画再生、旧セーブ移行を別に用意する。

## 合意前に確認する順番

まず設計の問題1・3・6・7を修正候補として検討する。特に**空認識でも刺激が判断へ届くこと**と**中間表現を出せない実装に架空の認識/動機を強制しないこと**が、現行実装を最小の互換層で載せる条件である。そのうえで税通知、命令、日次就労の3経路を紙上で再度通し、世界のEvent列・資産移動・人物の知識がどこで変わるか照合する。まだコード実装やv2契約の変更はしていない。

今回の検証はコードと文書の静的照合。前回の現行実装の型検査・28テスト成功は参照したが、この調査で新しい実行テストや性能計測は行っていない。
