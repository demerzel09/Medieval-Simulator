# 群雄と約束（仮題）— 企画・システム設計・実装引継書

版：0.1 / 作成日：2026-09-24 / 文書言語：日本語
対象：企画者、Codex、Claude Code、実装担当者
成果物の性質：実装開始に使う仕様案。ゲーム本体、性能検証、面白さの実証は未実施。

## 0. この文書の使い方

この文書を新規リポジトリの `docs/DESIGN.md` に配置し、第21章の開始プロンプトをコーディングエージェントへ渡す。最初の到達点は第17章のM0〜M3。全機能を一度に作らない。各段階で動作するゲームを残す。

### 要件の区別

- **合意した核**：会話でユーザーが示した構想。原則として実装者が変更しない。
- **実装用の仮決定**：この文書が具体化した方式・数値。まず採用し、実測やプレイ結果に応じて変更する。変更理由をADRに残す。
- **後続機能**：設計上の接続点だけ用意し、指定段階まで作らない。

文書内の係数、人口配分、マップ寸法、速度、報酬はすべてゲーム用の初期値であり、史実・人間心理の実測値ではない。歴史上の英雄が常に合理的だったという前提も置かない。

### 実装者が守る優先順位

1. ユーザーからの後続の明示指示。
2. 本文の「合意した核」とデータの不変条件。
3. 現在のマイルストーンの受入条件。
4. 仮決定の技術・バランス値。

矛盾を発見したら、核を維持する最小修正を行い `docs/DECISIONS.md` に記録する。新たな課金、公開配信、認証情報、外部サービス契約が必要なときは設定を保留してローカルの代替で進める。

## 1. 企画の要約

### 1.1 一文で表すゲーム

**欲望、文化、約束、人間関係で動く小国家を率い、全員を思いどおりにできない中で、必要な局面だけ協力と準備を成立させるストラテジー。**

プレイヤーは一人の君主として、徴税、褒賞、登用、遠征、大義の提示を行う。家臣・商人・地主・住民・兵士には固有の履歴があり、命令を自分なりに解釈する。会戦の結果には準備、人選、兵站、命令の伝達が大きく影響する。

少数の人物は、既定の候補を評価する通常AIに加え、状況に合わせて目標や複数手順の計画を考える。無名の人物が支持者を集めることもある。

### 1.2 合意した核

- Total Warに通じる国家運営と会戦の接続を持つ。
- 個人の欲望や人間関係を優先したくなる選択をプレイヤー自身に経験させる。
- 長期的に有利な選択には、短期の機会損失、譲歩、交渉、名誉の傷などが伴う。
- 一人ひとりの住民・兵士に固有の状態を持たせる。
- 目標規模は一国最大10,000人、軍籍を持つ者最大1,000人。兵士は人口の内数。
- 身分、文化、仕事、性格、経験によって正当性と利益の評価が違う。
- 徴税や徴兵への反応は、目的、約束、慣習、信用によって変わる。
- 大義が複数の集団に支持されれば、改革・反乱・革命・新勢力が成立し得る。
- ごく少数に、柔軟で一貫した意思を持つ人物を混ぜる。
- LLMは制作時のパターン作成と、限定された実行時の計画立案に利用できる。

### 1.3 面白さについての仮説

A. 選択の対価が「誰との関係を傷つけるか」として見えると、数値上の最適解を選ぶのが感情的に難しくなる。
B. 同じ政策でも、相手と約束の仕方によって結果が変わると、統治が人物理解のゲームになる。
C. 会戦後に「右翼の隊長に何を約束したか」が敗因として振り返れると、準備段階にも緊張が生まれる。
D. まれな人物が既存の資源・人脈から新しい連合を作ると、予定調和を崩せる。

これらは第18章のプレイテストで検証する。人口やパラメータを増やしただけでは成立しない。

### 1.4 重要な定義

本作の「合理的」は、国家の長期生存や戦争準備に有利という意味で用いる。ただし、個人の安全・名誉・家族・信仰にとって合理的な選択とは一致しない。全員に共通する唯一の最適解を前提にしない。

「苦痛」は、意味のある損失、葛藤、不確実性、政治的な譲歩を指す。反復クリック、分かりにくい画面、待ち時間の長さで作らない。

## 2. 舞台・プレイヤー・規模

### 2.1 仮決定

- 架空の前近代世界。通信は徒歩・騎馬の伝令。銃器、超自然能力なし。
- 初版は一代の君主を扱う90日間のシナリオ。成人中心の小国家。出生・老衰・世代交代は後続。
- 初期状態で家族関係は存在する。年齢は保持するが、90日シナリオで誕生・成人処理は行わない。
- 人口は世界内の実人数。初版は都市国家・小領邦の争いとして表現し、1人が100人を表す換算を用いない。
- 一時停止可能。戦略画面は時間送り。会戦は事前命令と遅延する追加命令で介入する。
- ローカルPCで動く2Dブラウザアプリを最初の実装対象にする。公開Webサービス化はこの依頼の範囲外。

### 2.2 規模を段階化

| 段階 | 人口 | 軍籍上限 | 国・拠点 | 柔軟な人物 |
|---|---:|---:|---|---:|
| M0〜M2 機構検証 | 自国600、敵国400 | 自国120、敵国80 | 2国、合計5拠点 | 0、Mockのみ |
| M3 遊べる試作 | 同上 | 同上 | 同上 | 0、通常AIで完結 |
| M4 社会の拡張 | 自国2,000、敵国1,000 | 自国300、敵国150 | 2国、合計8拠点程度 | 0〜3、Mock |
| M5 LLM接続 | M4と同じ | 同上 | 同上 | 同時最大3、設定で変更 |
| M6 規模拡張 | 最大3国×10,000 | 各国1,000 | 各国最大20拠点を基準 | 世界全体で同時最大8 |

M6の性能目標は世界全体30,000人で測る。「自国だけ1万人」で性能達成とはしない。会戦の描画対象は最大2,000人（2国が各1,000人）。複数会戦は同じ計算器で進行し、表示している一会戦だけ詳細描画する。

### 2.3 勝敗

試作のシナリオ目標：90日目に君主が生存し、首都を保有し、シナリオ内の争点である峠に対する自国の通行権が有効である。

通行権は占領または条約で獲得する。自国が峠を支配していれば通行権は自動成立。無血解決も勝利とする。兵数・領土最大化だけを唯一の評価にしない。

終了画面には、死者、生活の変化、履行した約束、失った友人、獲得した名声を並列で表示し、単一の総合スコアに換算しない。君主死亡・廃位・首都の継続占領24時間で敗北。廃位は反乱勢力の首都支配24時間と後継宣言の成立を条件にする。

## 3. プレイの流れと感情を生む設計

### 3.1 基本ループ

1. 届いた報告を読み、誰が何を求めているかを把握する。
2. 政策、任命、交渉、約束、軍の目的を決める。
3. 命令を送り、実行と反応を待つ。必要なら現地へ自分が赴く。
4. 利益・損失・信用の変化が、新しい支持や反発につながる。
5. 戦争や政治危機では、蓄積した関係と準備が試される。
6. 結果を報告と人物の反応から読み、次の判断をする。

### 3.2 プレイヤーが欲望を抱くための要件

| 誘惑 | 画面と出来事 | 実利 | 失う可能性 |
|---|---|---|---|
| 恩人を登用したい | 過去の救援記録と本人の願い | 信頼する家臣の協力 | 適任者の登用機会、部隊の安全 |
| 宿敵を討ちたい | 敵からの挑発、捕虜、因縁 | 支持者の結束、本人の達成感 | 兵站準備、外交上の余地 |
| 勝利を自分の手柄にしたい | 戦功報告と凱旋 | 君主の威信 | 将軍の不信、分配要求 |
| 目の前の仲間を救いたい | 個人名つきの救援要請 | 人命と信頼 | 予備隊、別方面の守備 |
| 新領土を取りたい | 支配地の変化、資源、人々の歓迎 | 収入と権威 | 統治負担、約束の履行負担 |

人物には顔代わりの紋章・名前・短い履歴を付ける。プレイヤーの判断と結びついた履歴を優先表示する。名声獲得には手応えを与えるが、慎重策にも「味方が無事帰った」「約束が守られた」という報酬を与える。

君主の性格と逆の行動を禁止しない。「冷静さポイント」を消費しなければ正しい命令が出せない設計は初版に採用しない。難しさは人間関係・準備・競合する要求から作る。

### 3.3 注意と委任

君主の現地面談・説得は1件2時間を要し、本人の移動時間も必要。文書命令の作成は1時間。通常の定例税・定例給与は自動継続する。日々の同じクリックを要求しない。

君主の作業は単一キュー。家臣へ委任可能で、家臣の信頼・文化理解・利害が結果に影響する。単純な操作数制限よりも、誰に任せるかの選択を生む。時間停止中もゲーム内時間を消費する作業は瞬時には終わらない。

## 4. 技術構成の仮決定

### 4.1 初期スタック

- TypeScript：シミュレーション、UI、テスト、データ契約を共有。
- React + Vite：情報パネルと操作画面。
- Canvas 2D：地図、部隊、兵士の描画。初期段階は専用3Dエンジンを使わない。
- Web Worker：権威あるシミュレーションを実行し、UI停止を防ぐ。
- Vitest：コアのテストと決定論的なシナリオ検証。
- IndexedDB：ローカルセーブ。JSON書き出し・読み込みも提供。
- Node.jsの小さなローカルサービス：M5以降のLLM接続だけ担当。APIキーはサーバー側の環境変数。
- JSON + JSON Schema：シナリオ、文化、規範、行動、LLM入出力を検証。

依存バージョンは実装開始時に互換性を確認して固定し、lockfileをコミットする。本書は特定の最新バージョンを要求しない。既存リポジトリがある場合は、核を満たす限りその構成を優先する。

Web Workerのメッセージ通信・DOMを直接扱わない性質はMDN、TypeScriptのプロジェクト分割は公式ドキュメントを参照する。ゲーム状態をUIから直接変更しない。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)、[TypeScript](https://www.typescriptlang.org/docs/handbook/project-references.html)、[Vitest](https://vitest.dev/guide/)

### 4.2 リポジトリ構造

```text
apps/web/                  # UI、Canvas、Worker入口
apps/llm-gateway/           # M5で作成。プロバイダー接続のみ
packages/sim/              # DOM、ネットワーク、UIに依存しないコア
packages/contracts/        # 型、JSON Schema、ID、メッセージ
packages/content/          # シナリオ、規範、行動テンプレート
packages/ai/               # 通常AI、計画器、Mock・LLMアダプター
packages/tools/            # headless runner、検査、ベンチマーク
fixtures/                  # 小さな固定世界と既知の期待値
artifacts/                 # テスト報告、性能結果。秘密情報禁止
docs/DESIGN.md
docs/DECISIONS.md
docs/STATUS.md
README.md
```

### 4.3 境界

`UI Command → validateCommand → command queue → simulation → events → player observation → UI`

AIも同じcommand経路を使う。UI・LLM・シナリオスクリプトが、人口、士気、所有権、勝敗を直接書き換えない。世界生成時の初期化だけ例外。

正確な世界状態 `WorldState` と人物が知っている `ActorObservation` は別の型。UIにはプレイヤー用Observationだけ渡す。開発モードだけ明示的に世界状態を閲覧できる。

## 5. 時間・更新順・再現性

### 5.1 時計

内部時刻 `worldMinute` は0以上の整数。戦闘の最小更新間隔は1分、戦略の定期更新は60分、経済は24時間。実時間の描画フレームと計算を分離する。

平時は次の予定イベントまたは時刻境界へ進める。会戦中は1分ずつ進め、同じ時計で60分ごとの戦略処理も動かす。会戦開始時に世界全体が無期限停止する仕組みは作らない。プレイヤーによる一時停止は全世界を停止する。

会戦の1分はゲーム上の抽象化。兵士のアニメーションは結果を補間して描画し、フレーム数で戦果を変えない。

### 5.2 同時刻の処理順

1. 期限到来の移動・伝令・建設などの到着を処理。
2. 到着した報告で人物の認識を更新。
3. 検証済みのCommandを適用（`executeAt, actorId, sequence`順）。
4. 戦闘があれば、更新前の状態から移動と戦果を計算して一括反映。
5. 60分境界なら、任務・政治行動・兵站移送・認識に基づく通常AIの判断。
6. 24時間境界なら、生産、給与、税、家計拠出・送金登録、市場取引、配給・消費、欠乏、約束を順に処理。7日境界では最後に文化学習を行う。
7. イベントを発行し、次回以降に届ける報告・記憶・判断要求を登録。
8. 不変条件検査、状態ハッシュ、UI差分生成。

同一時刻に生じた新しいAI判断は最短でも次の1分に実行。同時刻の自己生成イベント連鎖を禁止する。戦闘の死亡で給与対象が変わる場合、日次処理開始時の生存状態を用いる。

### 5.3 乱数と保存

- `Math.random()`、壁時計、ネットワーク到着順をゲーム結果の乱数に用いない。
- seedから明示的なPRNGを生成し、世界生成・人物選択・戦闘などのサブストリームに分ける。
- 保存対象：世界、時計、全キュー、PRNG状態、Command、未完了の約束、AI計画、LLM採用応答、仕様版、コンテンツハッシュ。
- まず同一エンジン版・コンテンツ版・実行環境で再現性を保証する。浮動小数の端数は定義した箇所で丸める。全プラットフォームのビット一致は未保証として明示する。
- セーブ再開後も同じ操作列なら同じイベント列・最終ハッシュになる。
- LLMを再呼出しして再現しない。採用済み応答と適用時刻を外部入力ログとして再生する。

## 6. データモデル

以下は実装必須の論理モデル。TypeScriptの全フィールド宣言ではない。IDは安定した文字列、金銭・在庫・人数・時刻は非負整数とする。0〜1の値はバリデーションで範囲を保証する。

### 6.1 人物

| フィールド | 内容 |
|---|---|
| id, name, age, alive | 固有ID、名前、年齢、生死 |
| legalStatus, roles[] | 身分と役職。将軍かつ地主などの兼任を許す |
| factionId, householdId, homeId, location | 国籍、世帯、故郷、現在地。捕虜は国籍と拘束主体を別保持 |
| cultureWeights | 複数文化への帰属の重み。合計1 |
| values | 安全、家族、富、名誉、信仰、忠誠、公平、支配の8次元、各0〜1 |
| temperament | 危険回避、忍耐、共感、疑い深さ、野心の5次元 |
| health, hunger, fatigue, fear | 身体・直近状態 |
| skills | 農業、工芸、商業、指揮、戦闘、交渉。初期は0〜100 |
| walletAccountId | 個人の金銭口座 |
| relationshipIds[] | 家族・知人・指揮関係への参照 |
| beliefIds[], memoryIds[] | 知っている情報と重要な経験 |
| commitmentIds[] | 自分がした約束・受益者としての約束 |
| activeGoal, planId | 現在の目標、計画 |
| planningMode | ordinary / deliberative。能力値とは独立 |

「忠誠」は一つの君主忠誠値で完結させない。君主、隊長、家族、共同体に対する関係を別に持つ。

### 6.2 社会・経済・軍事

| Entity | 主な内容 |
|---|---|
| Household | memberIds、住居、共有食糧、家計口座、扶養関係 |
| Relationship | from/to、信頼、好意、畏怖、恩義、種類、重要な関連イベント |
| Culture | 価値観の生成分布、Norm参照、儀礼、語彙。人格を固定しない |
| Norm | 適用条件、権利・義務、期待する対価、違反評価、認める権威 |
| Institution | 対象範囲、規則、執行担当、採用日時、支持者、変更手続 |
| Settlement | 所有国、人口索引、市場、貯蔵、施設、地形、接続道路 |
| Workplace | owner、職種、従業員、投入材、出力、在庫、賃金契約 |
| Faction | 君主、役職、国庫、制度、外交、支配地、政策 |
| Group | 村、宗派、商業組合、家臣団、政治運動など。所属は重複可 |
| Army / Unit | 指揮者、人物ID群、目的、所在、輸送在庫、編成、命令 |
| MilitaryAssignment | personId、unitId、従軍条件、給与、戦利品権、服務期限 |
| Promise | 第9章。履行状態と受け手の認識を分離 |
| Message | sender、recipient、出発・到着、経路、内容、発信根拠 |
| Belief | claim、source、取得時刻、確信度、最後に観測した時刻 |
| Movement | 発起人、大義、具体要求、勧誘経路、支持段階、動員力 |
| Event | id、時刻、kind、関係者、原因eventIds、変化、観測可能範囲 |

全員相互の関係行列を作らない。通常の社会接触は1人最大12件を初期値とし、家族・上司・重要な約束は削除しない別枠にする。有力者の関係増加には上限を設け、集団支持を併用する。

### 6.3 同一人物の継続性

住民を徴兵するとき新しい兵士を生成しない。既存PersonにMilitaryAssignmentを追加し、職場の稼働を停止または減らす。帰還後は同じ家族と記憶を持って職場に戻る。

死亡・捕虜・負傷・脱走・移住で人口所属、勤務、軍籍、給与対象を一貫して更新する。脱走兵は消去せず、位置と任務が変わる。人口上限に達した入国希望者は国境の抽象的な外部人口プールに留め、既存人物を黙って削除しない。世界内の実在人口と外部プールを集計上で区別する。

### 6.4 記憶と情報

通常人物の詳細記憶は最大20件、柔軟な人物は最大50件を初期値とする。超過した日常記憶は、出来事カテゴリ・相手・感情・回数へ集約する。未解決の約束、近親者の死亡、重大な裏切りは自動破棄しない。

記憶は `eventId, subjectiveInterpretation, emotion, source, confidence` を持つ。世界の真実と誤解を区別する。LLMが生成した解釈で、実際に発生した出来事を書き換えない。

## 7. 通常人物の意思決定

### 7.1 生成と評価

人物が実行できる候補行動を、役職、所在、知識、権利、資源から生成する。候補は初期最大8件。日常労働はルーチン、重大な状況変化で候補を再評価する。

初期の効用式：

```text
U_i(a) = Σ_k value_i[k] × expectedBenefit_i(a,k)
         + 0.8 × legitimacy_i(a)
         + 0.6 × relationshipEffect_i(a)
         - 1.0 × expectedBurden_i(a)
         - riskAversion_i × perceivedRisk_i(a)
         - 0.2 × switchingCost_i(a)
```

各入力は原則−1〜1、負担・リスクは0〜1。`expectedBenefit` は本人の認識から算出する。全知の将来損益は与えない。初期値は仮係数としてJSON化し、コードに散在させない。

直近行動を維持するヒステリシスを設ける。最良候補と現行行動の差が0.15未満なら現行行動を続ける。非常時の逃走・食糧欠乏は継続より優先する。候補の同点は安定IDで解決し、初版では毎回ランダムに選ばない。

### 7.2 文化と個人差

文化は価値観の初期分布、規範への接触、正当な権威の認識に作用する。同文化でも財産、家族、経験で判断が変わる。同じ文化の人を全員同じ重みにしない。

正当性 `legitimacy_i(a)` は、本人が知る規範のうち該当するものの加重平均。適用条件は行動、戦争目的、身分、場所、制度に依存する。利益があるだけで正当性が必ず上がる設計にはしない。

### 7.3 服従と支持を分ける

返答には `support / comply / bargain / delay / refuse / flee` を用いる。反乱や暴力は第11章の行動として別評価する。

恐怖による服従と、自発的な支持は別変数。抑圧で表面的な命令遵守が改善しても、正当性・情報の率直さ・次の危機での協力が改善するとは限らない。厳罰が必ず最適にも、必ず失敗にもならないよう、局所の執行力と逃げ道を入れる。

## 8. 経済・徴税・兵站

現行M1実装は国別共同事業口座などの簡略化を含む。平時の経済を人物の実働、所在地付き在庫、注文、運搬、受領時清算、所得の循環として段階的に検証する後続設計は[経済閉路の設計](ECONOMY_LOOP_DESIGN.md)を参照。以下の企画上の目標を実装済みと読み替えない。

### 8.1 最小経済

M1の財：食糧、木材、装備、通貨。人口の生産・消費・所有権を追う。食糧1単位＝成人1人の1日分、金銭1単位＝ゲーム内の整数通貨。市場価格は財ごとに最低1。

M1の初期生産：農民1人日あたり食糧3、木工1人日あたり木材2、工匠1人日あたり木材2から装備1。技能による倍率はM4で追加。日次割当の稼働人数を元に投入在庫を予約し、欠けた投入物では生産しない。従軍者・死亡者・捕虜は通常生産から外れる。

各世帯は稼働者賃金を受け取り、食糧を購入する。全員の行動計算を減らすため世帯単位で取引するが、配給、飢え、記憶は各Personへ戻す。初版では世帯内均等配給。出征者の食糧は軍が消費し、世帯の購入人数から除外する。

### 8.2 台帳と市場

財と通貨は口座／在庫間の移転として記録する。生産・消費・初期生成・外部交易だけが総量を増減できる。借金を所持金の負数で表さず、債務レコードにする。融資は貸手から借手への実際の通貨移転と、元本・固定利息額・返済期限を持つ返済Promiseを一体で登録する。貸手の資金を超える融資は成立しない。貨幣発行は初版に入れない。

M1は固定価格の市場。M4で価格更新を入れる：

```text
nextPrice = clamp(round(price × (1 + 0.1 × (demand-supply)/max(demand,supply,1))), minPrice, maxPrice)
```

全注文を集めてから、一つの価格で清算。買い手は所持金、売り手は在庫を上限とする。供給不足は購入可能需要に比例配分し、整数の余りは日ごとに回転する安定ID順で配る。常に同じ世帯だけ飢える順序バイアスを避ける。清算前に在庫・現金を予約して二重利用を防ぐ。

### 8.3 徴税

定例税は所得比率、臨時税は世帯別の定額または食糧現物。初版の定例税は稼働賃金の10%。税率変更は周知Message到着後から適用する。

納税への反応は、目的、生活余力、文化上の負担義務、税の使途の認識、君主への信用による。`徴税額→一律不満`を禁止する。拒否された税は自動入金しない。徴税人による再交渉・執行には時間と人員が必要。

### 8.4 徴兵と報酬

徴兵募集は目的、人数、服務期限、給与、戦利品分配、家族扶助を含む契約。役職・文化で条件評価が異なる。1人の候補が複数部隊に同時加入しない。

兵役による生産減と、給与・家族扶助による需要増を同時に扱う。軍用装備は保管庫から人物へ移転。死亡後の装備回収は戦場支配と回収作業で決める。

### 8.5 兵站

軍の在庫は出発拠点から運ぶ。輸送も位置・時間・運搬能力を持つEntity。国庫に食糧があるだけでは前線で消費できない。補給が来なければ兵士ごとに欠食日数、疲労、信頼変化を更新する。平時の経済と軍兵站で物資・容器・運搬・受領・消費の正本を共有する移行設計は[共通物流設計](COMMON_LOGISTICS_DESIGN.md)に記す。現行M2の補給口座とE1の実物流通はまだ別世界である。

初版の行軍は道路グラフで距離を時間に変換。軍の平地速度2km/h、伝令6km/h、荷車2km/hを仮値とする。休息なし24時間移動は疲労で制限。道路・峠・橋の通行権を検査する。敵支配地への荷車の自動通過は禁止。

## 9. 約束・文化・制度

### 9.1 Promiseの必須項目

```text
id / promisorId / beneficiarySnapshot[] / witnessIds[]
createdAt / deliveredTo[] / kind / terms / trigger / dueAt
escrowAccountId? / guaranteedBy? / status
fulfilledAmount / sourceEventIds[]
```

`kind` は固定給与、現物支給、戦利品分配、家族扶助、役職任命、通行権、減税、権利付与、融資返済。`status` は proposed / active / due / fulfilled / breached / renegotiated / void。

受益者は契約成立時に確定し、後から集団に加入して自動的に分け前を得ることを防ぐ。任務ごとに「参加者」を定義し、死亡者の権利を相続するかも明記する。

### 9.2 条件と履行

- 「勝ったら分配」は、勝利条件と分配対象の台帳を指定する。
- 勝利条件を満たさないとき、その約束は未発動。約束違反にはしない。ただし期待外れによる失望は別の小さな反応を許す。
- 発動した義務が期限まで履行されなければ違反。不可抗力・弁明・再交渉を受け手がどう評価するかは個別に計算する。
- 政策を命じただけでは履行にならない。減税なら対象者に実際に適用された徴税記録、役職なら権限移転イベントで確認する。
- 約束の撤回は記録を消さない。相手が同意した再交渉は旧約束への参照を持つ新Promise。

報酬信頼の初期式：

```text
credibleReward = promisedReward × perceivedSuccess × trustInPromisor
trustAfter = clamp(trustBefore + 0.08 × fulfilledSeverity - 0.20 × breachedSeverity, 0, 1)
```

severityは0〜1、該当しない項は0。更新は本人が結果を知った時点で一回のみ。重複した噂で何度も信頼を下げない。

### 9.3 分配の整数規則

戦利品は所有権移転済みの財・通貨のみ。架空の「勝利報酬」を自動生成しない。分配率の合計は100%以下。同じ資産への約束が100%を超える契約も、欺瞞として明示的に発行は可能とするが、重複債務として警告・台帳記録し、支払い時に無から補填しない。

初版の清算順は契約作成時刻順。契約内では持分に比例配分し、小数を切り捨て、端数はpersonId順に1ずつ配る。分配後に残額が保存されることを検証する。保証金は予約済みとして通常支出に使わせない。

### 9.4 規範の具体例

| normId | 適用条件 | 期待 | 違反として感じるもの |
|---|---|---|---|
| home_defense | 故郷が侵攻対象 | 君主が防衛を優先し、住民も協力 | 遠征のため故郷を見捨てる |
| expedition_share | 国外遠征への参加 | 戦利品の事前に合意した分配 | 勝利後の横取り |
| service_honor | 奉仕と戦功の報告 | 公的な承認、適切な役職 | 戦功の剽窃、侮辱 |
| paid_service | 給与契約が存在 | 定期の支払い、服務期限 | 遅配、無断延長 |

同じ人物が複数規範を持ち、衝突し得る。単なる文化別の固定加点表にしない。

### 9.5 文化変化（M4以降）

制度は宣布で変えられるが、規範への個人の支持は経験と伝播で変わる。週次で関連する履行・違反イベントからnormEndorsementを更新する。初期最大変化量は週0.02。重大な危機は別の一回限りイベントとして上限0.10。全員同時には変化しない。

給与制を長期に守れば、その制度の経験者が給与支払いを権利として期待するようになる。周囲の成功例や信用する相手の発言で伝播する。出生・世代継承は後続。

## 10. 指揮・通信・会戦

### 10.1 情報の非対称性

本人の現在位置から見える範囲、受け取った報告、過去の記憶だけを使う。報告には観測時刻と発信者を表示する。敵戦力は推定範囲として届く。

通常AI・柔軟AI・プレイヤーに同じ観測規則を適用する。AIへ未知の敵位置や隠された陰謀を渡さない。消息不明は壊滅と同義にしない。

### 10.2 命令

Orderの必須項目：issuer、recipient、intent、target、fallback、発令・到着時刻、期限、優先順位、交戦規定。

命令の選択肢：守備、進軍、偵察、待機、攻撃、撤退、護衛、徴発。条件付き命令は「敵兵数推定が自軍の1.5倍以上なら撤退」「補給残量が2日分未満なら帰還」など、受け手が観測できる条件に限る。

命令を読んだ指揮官は、服従、確認要求、修正提案、拒否を選ぶ。上官への忠誠だけでなく、目的、家族、兵士の状態、独断の許容範囲で評価する。命令変更の伝令も移動する。プレイヤーのクリックによる瞬間的な全軍方向転換はできない。

### 10.3 戦闘の初版仕様

M2では64×64セル、1セル50mの地形。平地・森林・高地・川・橋・撤退口を持つ。戦闘開始地点の戦略地形から生成する。10〜20人を1部隊とし、経路探索は部隊単位。各兵士のID、健康、士気、装備、位置オフセットを保持する。

- 兵種は歩兵のみ。M4以降に弓兵・騎兵。
- 部隊の接敵と側面判定をセルで処理。
- 全兵士同士の総当たり衝突判定を行わない。
- 戦闘の攻撃量は更新開始時の状態で決め、同一tickの双方の損害を一括適用する。
- 戦死・負傷対象をseed付き乱数で生存者から抽出。死亡処理は冪等。
- 逃走は士気・恐怖・仲間・逃走経路で判断。士気平均だけで個人差を消さない。

最初の計算式：

```text
power(unit) = readyCount × (0.5 + meanSkill/100)
              × (0.5 + meanMorale)
              × (1 - 0.5 × meanFatigue)
              × terrainFactor × flankFactor × equipmentFactor
expectedCasualties(A→B) = min(B.aliveCount, 0.01 × power(A) × exposure(B))
```

terrainFactorは0.7〜1.3、flankFactorは正面1.0・側面1.25・背面1.5、equipmentFactorは無装備0.6・装備あり1.0、exposureは0〜1。小数部分を確率丸め。初期は損害の30%戦死・70%負傷とし、医療の詳細は後続。これらは戦闘時間を調整する仮値。

士気更新の初期入力：直近5分損害率、指揮官生存、周辺味方の逃走率、疲労、補給、個人の恐怖、隊長への信頼。係数はcontent側で定義し、接敵前から全員が同じ士気になる実装を避ける。M2でまず固定係数を明文化する。

### 10.4 終結と戦略への復帰

一方が戦場から撤退／戦闘継続部隊を失う／降伏すると終結。6時間を上限とし、双方が残れば決着なしで戦線を維持する。撤退路を持たず、敵に隣接し士気0.1未満の兵士は降伏候補。捕虜の維持食糧も必要。

占領、負傷、捕虜、戦利品、約束の発動、家族への報告を同じPerson・台帳へ戻す。戦果報告の到着まで君主は正確な死者数を知らない。

撤退後は6時間の再編成状態。無限に戦場を出入りして戦闘判定を回避する操作を防ぐ。オート解決も同じ計算器を描画なしで実行する。

## 11. 大義・政治運動・革命

### 11.1 大義の表現

大義は文章と機械可読の要求からなる。初版の自由文は説明・演出用途。世界を変える効果は必ず構造化する。

```text
Cause:
  grievanceTags[]    # 税負担、約束違反、故郷放棄、身分差など
  audienceGroupIds[]
  proposedChanges[]  # 減税、給与制度、役職変更、通行権、身分権利
  promises[]
  speakerId
  narrative          # 上記を表現する文章
```

文章に「すべての人が支持する」と書いても効果はない。新規制度は既定の効果語彙の組み合わせで構成する。任意の文章から任意のゲームルールを作ることは初版の範囲外。

### 11.2 個人の支持と行動

支持段階：unaware → aware → sympathizer → supporter → mobilized。離脱・転向も可能。賛同と武装参加は分ける。

初期評価：

```text
appeal = 0.30×grievanceMatch + 0.20×normFit
         + 0.20×speakerTrust + 0.15×expectedGain
         + 0.15×perceivedPeerSupport
joinScore = appeal - 0.40×repressionRisk - 0.20×opportunityCost
```

入力は0〜1。通常はappeal≥0.5で共感、joinScore≥0.45で支援、武装参加はさらに装備・集合命令・本人の危険許容を満たす必要がある。解除閾値は加入より0.1低くし振動を避ける。M4で調整する。

周囲の支持率は本人が接触した集団・知人から推定し、世界の本当の支持率を使わない。高い支持率の噂が誤報の可能性も持つ。

### 11.3 組織化

日次で各活動家は最大3人または1集団代表に接触。接触には同拠点・Message・集会が必要。反乱軍は現存Personの加入で形成し、兵が無から現れない。平時の仕事を離れれば生産は減る。

蜂起には発起人、集合場所、集合時刻、食糧、実際に集まった人員が必要。M4の初期成立条件は20人以上、1日分の食糧、指揮者。条件未達なら延期・解散・地下活動を判断する。

政治運動の目的は減税、制度変更、領主交代、独立、君主交代を区別する。反乱がすべて国家滅亡へ直行しない。交渉による譲歩で沈静化できる。

### 11.4 革命後

政権が変わっても約束は消えない。新政権の支持者に相反する約束があれば、減税・給与・地主権の衝突が残る。国庫と生産能力は引き継ぐため、支持のために約束した利益をすべて実現できるとは限らない。

## 12. 柔軟な人物とLLM

### 12.1 設計目的

通常AIは既存候補を評価する。柔軟な人物は、本人の知識・人脈・価値観から、目標、相手、約束、行動順を組み合わせる。例：商人に食糧供給を約束させ、住民の支持を取り付け、徴税拒否から自治交渉へ進む。

柔軟であることを賢さ・成功・英雄性と同一視しない。思い込みによる失敗や、合理的に見えて本人の名誉を損なう案を拒否することも許す。

### 12.2 起動対象と頻度

- 引き金：重大な敗戦、近親者の死、約束違反、昇進・独立の機会、政治的な勧誘、現在計画の行き詰まり。
- 新規起動者の選定：引き金の重大さ×個人への関連度×行動可能性。権力だけで選ばない。
- 同時枠のうち最低1枠を非上層身分の候補に割当可能にする。該当候補なしなら空ける。
- 選定は本人が観測した出来事から行い、世界の隠れた危機を教えない。
- 1人につきゲーム内24時間に1回を原則。命に関わる例外も世界全体の予算内。
- 再考待ち・枠落ちでも、既存計画と通常AIで行動を続ける。人物や人格が消えない。

### 12.3 入力契約

```text
DeliberationRequest:
  requestId, actorId, snapshotVersion, requestedAt, applyAt
  observation                  # 本人に見える世界のみ
  coreValues, temperament
  relationshipsSummary        # 対象人物と根拠eventIds
  relevantMemories
  activePromises, activePlan
  availableActionSchemas
  resourceAndAuthoritySummary
  maxPlanSteps: 4
```

人格の文章だけに一貫性を依存しない。価値観、約束、重大な記憶はゲームの構造化状態として保持する。長い内部推論の出力を要求せず、行動理由は短い要約と根拠IDでよい。

### 12.4 出力契約の例

```json
{
  "requestId": "req_014",
  "actorId": "p_captain_02",
  "snapshotVersion": 128,
  "goal": "故郷を守り、部下を帰還させる",
  "rationaleSummary": "防衛要請を受けたが増援は未確認。村への義務を優先する。",
  "evidenceIds": ["belief_17", "memory_03"],
  "steps": [
    {"action": "SEND_MESSAGE", "targetId": "p_lord_01", "args": {"templateId": "request_redeploy", "locationId": "s_home"}},
    {"action": "WAIT", "targetId": null, "args": {"minutes": 120}},
    {"action": "MOVE_UNIT", "targetId": "u_02", "args": {"destinationId": "s_home"}}
  ],
  "abortConditions": [{"kind": "UNIT_DESTROYED", "targetId": "u_02"}],
  "reconsiderAfterMinutes": 1440
}
```

この例は通信後に独断撤退する計画であり、部下が必ず従う保証はない。WAIT後に権限、位置、命令競合を再検証する。将来の世界状態を予言して作った条件を受け付けない。

### 12.5 実行できる行動

M5の語彙：SEND_MESSAGE、PROPOSE_PROMISE、ACCEPT_PROMISE、REQUEST_AUDIENCE、ASSIGN_ROLE、MOVE_UNIT、ISSUE_ORDER、TRANSFER_RESOURCE、PROPOSE_CAUSE、RECRUIT_SUPPORT、NEGOTIATE、WAIT。

LLMに任意コード実行、WorldState直接編集、自由なスクリプト登録を与えない。新しい大義は既存の要求・約束・相手を組み合わせる形で実現する。未実装の行動提案はログに残し拒否する。語彙にない戦術を実際に実行できるとは表示しない。

### 12.6 検証パイプライン

1. JSON Schemaと文字数・step数を検査。
2. actor/request/snapshotの一致、ID存在、本人の既知情報を検査。
3. 行動の権限と資源を検査。上官の命令を破ることと、その部隊を指揮する権限がないことは区別する。
4. 価値観や約束との矛盾があれば「禁止」ではなく重大な葛藤として記録。核心目標の変更には関連する出来事を要求し、無根拠の急変は一度だけ再生成。
5. 最長4手のPlanを登録。各手を実行直前に再検証。
6. 失敗した手は理由を記録し、継続・中止・再考へ。成功や他人の服従を強制しない。

### 12.7 遅延・費用・再現性

初期上限：世界全体でゲーム内1日6要求、1要求入力4,000・出力800トークン程度、同時接続2、実時間20秒タイムアウト。これらは設定値であり、特定モデルの価格・速度の保証ではない。

要求時に `applyAt = requestedAt + 60分` を固定する。期日までに受け取った妥当な応答だけ採用し、届かなければ通常AIへ戻す。ゲーム速度によって採否が変わることは外部入力ログに記録する。比較実験とリプレイはMockまたは録画済み応答で行う。

有効化前に、プロバイダー、モデル名、1日／セッションの金額上限をユーザーが設定する。金額上限未設定なら外部呼出しを行わない。呼出し前に最大消費額を予約し、実績で精算する。API失敗で無限再試行しない。予算・接続がなくても全ゲームが進行する。

キーはLLM gatewayの環境変数のみ。ブラウザのバンドル、セーブ、ログへ含めない。モデルの返答は演出文でも命令として解釈せず、Schema経由で扱う。

### 12.8 制作時LLM

制作時に文化・規範・対立・台詞・ケースを生成し、検証済みJSONとして固定する。必須出力は適用条件、対象、期待、違反、例外、反例、関連行動ID、検査シナリオ。

生成案は人間が採用を決める。史実を掲げる場合は出典を別途確認する。架空文化でも「全員が同じ性格」という内容は採用しない。コンテンツ検査で到達不能な条件、存在しないaction、支払えない自動報酬を検出する。

## 13. UI・観測・説明可能性

### 13.1 必須画面

1. **戦略地図**：拠点、経路、既知の軍、伝令、選択対象、時間操作。
2. **君主の執務画面**：報告、面談、任務キュー、未回答の提案、約束の期限。
3. **人物画面**：関係、役職、見えている履歴、要求、本人の発言。
4. **約束台帳**：相手、目的、条件、期限、保証、実際の履行、争点。
5. **経済画面**：国庫と世帯生活を分け、在庫、物流、欠乏の分布を表示。
6. **会戦準備・戦闘画面**：地形、人選、編成、命令、伝令到着、推定状況。
7. **出来事の振り返り**：意思決定、伝達、反応、戦果の因果を辿る。

### 13.2 表示ルール

- プレイヤーに他人の本心・正確な効用値・反乱確率を通常表示しない。
- 性格は「複数の行動から慎重と思われる」など、観測根拠を示す。
- 報告には「いつの観測か」「誰から聞いたか」「確かさ」を付ける。
- 命令前の表示は、既知の直接費用、権限、相手の既知の要求、あり得る反応。未来の正解を表示しない。
- 不明な理由を偽の説明で埋めない。「隊長から返答なし」「後日兵士の証言で判明」を許す。
- プレイヤーが知らない因果eventは、後から証言が届いたときに振り返りへ追加する。
- 開発モードには完全な効用内訳・資源移動・原因eventIdsを表示する。通常モードと視覚的に区別する。

### 13.3 画面の優先順位

M3までは地図、報告、人物、約束、戦闘、終了の6画面でよい。住民1万人を一覧で毎回描画しない。人物一覧は絞り込みと仮想化、地図は縮尺に応じて集団表示。日本語の読みやすさと文字による状態識別を優先し、色だけで敵味方・危険を区別しない。

## 14. 最初のシナリオ「峠と収穫」

### 14.1 世界

自国アウル600人、隣国ベル400人。自国に首都・農村・交易町、敵国に城下町・峠の砦の計5拠点。峠は交易路であり、地形上の要衝。初期は敵国が通行を禁止している。

開始時に全人口は成人。1人ずつ名前、家族関係、職業、文化帰属、財産をseedから生成。自国の軍籍上限120、敵国80。初期軍籍は自国40、敵国30で、労働力から除外する。

敵君主は定例日次の通常AIで、軍の補充、防衛、通行交渉を評価する。プレイヤーと同じ資源を使い、毎日軍隊や資金を補充しない。

### 14.2 初期経済

- 食糧備蓄：各国人口×12日分。うち世帯2日分、残りは国庫・職場・市場に割当。
- 総通貨：各国人口×100。国庫30%、世帯40%、職場・商人30%。生成時に所有者別に割当し、総量を検査する。
- 職業の初期割合：農業45%、木工10%、工匠10%、交易・輸送10%。残りは行政、軍、無職等。すべてのカテゴリを排他的な主職として合計人口に一致させる。
- 初期在庫の木材は各国人口×2、装備は初期軍籍人数＋予備20。軍籍人物へ支給した分は倉庫から差し引く。
- 食糧価格2、木材価格3、装備価格12、通常賃金3/日、兵士給与4/日。臨時軍費の募集は選択制。
- 所有者と生産原価を含む収支をM1で測り、固定価格でもシナリオが必ず破綻するなら調整理由を記録する。

職業割合は軍を含めた初期割当後に農業等を調整する。指定合計が超過する設定はロード時に拒否する。空欄を都合のよい追加人口で埋めない。

### 14.3 主要人物

| 人物 | 立場と関係 | 欲求・懸念 |
|---|---|---|
| 君主 | プレイヤー。先代の峠攻略失敗を引き継ぐ | 威信回復、国家維持 |
| 古参将軍 | 先代の恩人、君主への信頼は高い | 奉仕の名誉、戦功の承認 |
| 農村出身の隊長 | 村人から信頼される | 家族と故郷の防衛、無意味な犠牲の回避 |
| 有力商人 | 交易町の輸送を握る | 通行権、契約履行、予測可能な税 |
| 地主 | 農地と雇用を持つ | 労働力確保、財産権 |
| 敵国の領主 | 峠を守る | 領地と威信。条件次第で条約に応じる |

主要人物以外にも同じデータモデルの一般人が存在する。主要人物だけが世界を回す脚本にしない。

### 14.4 初期の選択と分岐

- 臨時徴税して早期遠征。
- 商人に通行権獲得後の交易条件を約束して融資交渉。
- 戦利品分配を約束して志願兵を募る。
- 敵に通行料・捕虜返還・相互不可侵を提案する。
- 収穫と訓練を待つ。その間に敵も補強や交渉を進める。

戦利品分配は敵が実際に保有する資産を期待する。外交による勝利では戦利品の約束は発動しない可能性がある。外交に切り替えるとき、従軍者に別の対価を提案する余地を残す。

### 14.5 固定ケースと通常ゲームを分ける

開発用fixtureには「約束を破った直後」「給与を全額支払った直後」などの小世界を用意する。通常ゲームでは条件を満たした結果として発生させる。必ず特定日に裏切る、必ず敗戦する、などの脚本を基本ループの代用にしない。

## 15. API・コンテンツ契約

### 15.1 Command

```ts
type CommandEnvelope = {
  id: string;
  actorId: string;
  issuedAt: number;
  executeAt: number;
  sequence: number;
  kind: string;
  payload: unknown; // kindごとのSchemaで検証してから型へ変換
  origin: "player" | "ordinary_ai" | "deliberative_ai" | "system";
};
type CommandResult =
  | { ok: true; commandId: string; eventIds: string[] }
  | { ok: false; commandId: string; reasonCode: string; detail: string };
```

reasonCode初期セット：UNKNOWN_ACTOR、UNKNOWN_TARGET、NO_AUTHORITY、INSUFFICIENT_RESOURCES、OUT_OF_RANGE、STALE_PLAN、INVALID_CONDITION、ALREADY_APPLIED、ACTOR_UNAVAILABLE。

個別kindはdiscriminated unionへ展開する。許可リスト外のkindは拒否。idempotency keyにより再送で二重払い・二重徴兵が起きない。

### 15.2 Event

```ts
type DomainEvent = {
  id: string;
  worldMinute: number;
  kind: string;
  actorIds: string[];
  causes: string[];
  payload: unknown;
  visibility: { directWitnessIds: string[]; reportable: boolean };
};
```

Eventは実際の変化。Reportは人物へ届く情報。Eventのvisibilityだけで全員に即配信しない。噂・報告がMessageとして伝わる。

### 15.3 初期Command一覧

M1：SET_TAX、PROPOSE_PROMISE、ACCEPT_PROMISE、TRANSFER_RESOURCE、ASSIGN_JOB、RECRUIT、DEMOBILIZE、SEND_MESSAGE、ADVANCE_TIME。
M2：ASSIGN_COMMANDER、ISSUE_ORDER、MOVE_UNIT、DISPATCH_SUPPLY、SURRENDER。
M3：REQUEST_AUDIENCE、NEGOTIATE、ASSIGN_ROLE。
M4：PROPOSE_CAUSE、RECRUIT_SUPPORT、DECLARE_MOVEMENT、ENACT_INSTITUTION。

LLM用のWAITはPlanExecutor内部の待機であり、世界を止めるCommandではない。ADVANCE_TIMEはユーザーのシミュレーション操作で、人物の能力ではない。

### 15.4 コンテンツ検証

起動時に全ID参照、条件の型、資源、役職、財の単位、配分、上限を検査。文化・大義の条件DSLはall/any/not、比較、タグ包含のみで開始する。`eval`を使わない。数値のNaN、Infinity、負の在庫、無期限ゼロ時間ループを拒否する。

セーブはschemaVersionを含み、互換性がない版は明確に拒否する。初版から旧セーブを無断リセットしない。移行機能は必要になった版で追加する。

## 16. 性能・ログ・診断

### 16.1 予算

以下はM6の設計目標で、計測済みではない。実装開始時にCPU・RAM・OS・Node・ブラウザの版を記録した基準機を決める。

| 条件 | 初期目標 |
|---|---|
| 世界30,000人の日次経済＋社会更新 | p95 250ms以内、headless、LLM通信を除く |
| 戦闘2,000人の1分tick | p95 30ms以内 |
| UI応答 | 通常入力100ms以内。重い集計は非同期 |
| 描画 | 基準機で30fps以上を目標 |
| プロセス使用メモリ | 1GB以内を目標。ログ無制限を禁止 |
| ローカルLLM無効 | 接続なしで開始・90日完走・保存可能 |

目標未達なら処理別時間を測り、候補探索、経路、ログ、描画、コピーのどれが律速かを示す。性能のために人物IDや約束の履歴を黙って消さない。

### 16.2 計算量の制御

- 常時処理は人物数と既存関係数にほぼ比例するようにする。
- 人物間接触は疎なグラフ、戦場は空間索引、経路探索は部隊と輸送単位。
- 平時の歩行を全員セルごとに再現せず、所在・行程・到着時刻で扱う。
- 全員の全行動候補を毎分評価しない。日常は日次、警戒・軍事は時間／イベント単位。
- UIへ全WorldStateを毎フレームコピーしない。選択対象・集計・差分を送る。
- LLMは深い判断の一部だけ。メモリ・経済・戦闘の数値処理に使わない。

### 16.3 記録

毎tickの全状態を保存せず、Command、重要Event、PRNG、周期snapshotを使う。日次の大量な経済イベントは世帯・職場単位の帳票へ圧縮し、取引IDと保存則は維持する。重要な政治・戦闘・約束の原因リンクは残す。

1回のベンチマークはウォームアップ10日＋計測100日、複数seedで実行。平均だけでなくp50/p95/最大とメモリを報告する。LLMを含む場合は通信時間・トークン・失敗率を別掲。

## 17. 実装バックログと受入条件

### M0：再現可能なコア

**作るもの**：リポジトリ、型、ID、PRNG、時計、キュー、Command検証、Event、セーブ、headless runner、生成器。
**受入**：100人の固定世界を30日進められる。同じseed・Commandでハッシュ一致。中間保存から再開して同じ結果。UI不要。
**作らないもの**：LLM、3D、複雑な戦闘、世代交代。

### M1：生活・約束・徴兵

**作るもの**：世帯、仕事、生産、市場、賃金、税、家族、規範、Promise、軍籍、報告、通常AI。
**受入**：600＋400人を30日運転。同額徴税でも規範と目的で反応が変わる。約束成立・履行・違反が信用に影響。徴兵で生産が減り、帰還で復帰。通貨・食糧の保存則を検査。簡単な検査UIを用意。

### M2：戦争と通信

**作るもの**：地図、伝令、偵察、経路、補給、命令、歩兵会戦、死亡・負傷・捕虜、分配。
**受入**：同じ部隊でも初期配置・補給・命令到着の差で、設計どおりに結果が変わるfixtureがある。両軍最大200人を追跡。会戦中も世界時計が進む。兵士が帰還後に元の家族を持つ。

### M3：最初の遊べる版

**作るもの**：「峠と収穫」90日、必要UI、外交、終了画面、チュートリアル、出来事の振り返り。
**受入**：新規開始から勝利／敗北まで通常AIで完走。軍事・外交の両経路を実行ログで確認。約束の履行と人物関係が少なくとも一つの主要判断を変える。第18章の人間テストを行う。
**納品**：起動方法、テスト結果、既知制限、スクリーンショット、サンプルセーブ。

### M4：政治運動と文化変化

**作るもの**：大義、接触、賛同と参加の分離、組織化、交渉、反乱、制度、週次規範学習、3,000人世界。
**受入**：同じ大義でも人物により支持が異なる。高い不満だけでは蜂起しない。集団間の協力と物資があれば蜂起が成立。政権交代後も債務・約束が残る。

### M5：少数の柔軟な人物

**作るもの**：Plan、Mock、入力フィルター、LLM gateway、予算、外部入力ログ、フォールバック。
**受入**：Mockで既定候補にない組み合わせ計画を実行。権限のない命令は拒否。未知情報が入力に入らない。タイムアウトでも完走。LLM有無の比較報告。人物の急変・計画失敗を観測できる。

### M6：人口・会戦規模の拡張

**作るもの**：世界30,000人、各国軍籍1,000、2,000人会戦、最適化、一覧仮想化。
**受入**：第16章のベンチマークを実施し、達成／未達を記録。小世界と同じ保存則・セーブ・情報制約を維持。人数を増やすだけでイベント洪水や操作量が破綻していないことを人間が確認。

### M7：後続の選択肢

出生・老衰・継承、複数時代、弓騎兵、海運、宗教組織、土地市場、より自由な制度、モッディング、デスクトップ包装。M0〜M6の品質が足りない間は着手しない。

## 18. 検証計画

### 18.1 不変条件テスト

| ID | 入力・状況 | 必須結果 |
|---|---|---|
| INV-01 | 徴兵、帰還、死亡、捕虜を連続実行 | 人物IDが重複せず、国人口と所在の集計一致 |
| INV-02 | 取引・税・給与・略奪 | 通貨の総量が保存。外部交易は外部勘定込みで一致 |
| INV-03 | 生産・食事・輸送 | 前在庫＋生産−消費−損耗＝後在庫。負数なし |
| INV-04 | 同じCommandを2回送信 | 支払・徴兵・命令登録が一度だけ |
| INV-05 | 保存→再開 | 続行とイベント列・ハッシュ一致 |
| INV-06 | 敵の秘密だけ変えた二世界 | 本人のObservationが同一なら通常AIの判断入力も同一 |
| INV-07 | 同一Promiseの噂が反復到着 | 同じ履行・違反で信頼を重複更新しない |
| INV-08 | 死亡者・捕虜へ勤務指示 | 生産・給与・軍籍の規則に従い拒否／停止 |

### 18.2 行動の対照実験

- BEH-01：同財産・同関係・同税額で、規範だけが異なる二人物。防衛負担／遠征負担の評価差がある。
- BEH-02：同文化・同税額で、履行履歴だけを変える。報酬約束の信頼が変わる。
- BEH-03：同文化で扶養家族・欠乏状態を変える。徴兵への反応が変わる。
- BEH-04：同じ平均不満でも、相互接触なし／信用する指導者ありで組織化が違う。
- BEH-05：約束の条件未発動では違反扱いしない。期限到来後の未払は違反。
- BEH-06：隊長の故郷防衛規範と君主忠誠が衝突。任務の優先が状態によって変わる。
- BEH-07：同seedと戦力で補給・地形・伝達遅延を独立に変え、意図した方向の差をfixtureで確認。

各fixtureは必要変数だけを変える。世界全体が常に想定方向へ動くと断言するテストにはしない。副作用は別ログで観察する。

### 18.3 具体的な約束fixture

8人の従軍者に、勝利後の戦利品100通貨の40%を均等配分する契約。

- 勝利し、実際に100通貨を獲得：合計40支払い、1人5、残額60。
- 勝利せず戦利品なし：未発動。違反ではない。
- 勝利・100獲得後、期限まで20しか配らない：不足20。違反反応は受益者が知った時に発生。
- 同じ支払Commandを再送：追加支払なし。
- 戦死者の取り分は契約の相続条項に従う。受益者から勝手に削除しない。

### 18.4 LLM・計画器テスト

不正JSON、未定義行動、知らない敵ID、資源不足、他人の部隊、過去のsnapshot、API停止、予算超過、遅着、同応答の再適用、保存中の未完了要求を含める。

人物一貫性は「必ず同じ行動」を正解にしない。重要な約束を見落としていないか、目標変更に理由があるか、事実を捏造していないか、情報・権限の制限内かを検査する。実モデルは非決定的なので、厳密テストは録画応答とMockで実行する。

### 18.5 人間による面白さの判定

M3で3〜5人に30〜60分の試遊。開発者による解説なしで観察し、次を記録する。

- プレイヤーが名前を覚えた人物が2人以上いたか。
- 「長期的には不利そうだが、この人物／目標のために選んだ」判断があったか。
- 予想外の結果について、本人が因果を一つ以上説明できたか。
- 命令の遅延を、意味のある戦略上の制約として理解できたか。
- 意図した不確実性と、UI不足による混乱を区別できたか。
- 同じ選択だけ繰り返せば勝てると感じたか。

これは統計的な有効性の証明ではなく、設計上の大きな失敗を早期に見つける試験。最適化が面白さを圧倒する場合は、まず人物との接点、相反する利益、結果の見せ方を修正する。隠し乱数で解決しない。

## 19. リスクと設計上の限界

| リスク | 兆候 | 対応 |
|---|---|---|
| 人口だけ増えて人物が無意味 | 住民を見なくても政策の最適解が同じ | 部隊・世帯・約束を通じた個人差の経路を増やす |
| 説明不能な混乱 | 何が原因か誰も分からない | 観測・報告・因果ログを改善。隠された事実は後から届くようにする |
| 全員が短期利益最大化 | 文化差が利得の名前違いになる | 義務・権利・恩義・侮辱を独立した評価軸に残す |
| プレイヤーだけ全知 | 人物を直接覗いて最適な命令を出せる | Observation経由のUIとAIを徹底 |
| LLMが自由すぎる | 存在しない権限や物資で計画成功 | 共通Commandと実行前再検証 |
| LLMが常に妥協的・有能 | 全員が似た調停案を出す | 人物別価値、誤認、局所情報を入力し、通常AIとの比較を行う |
| 少数人物が脚本上の英雄になる | 常に選ばれ、常に支持される | 起動枠を動的選定し、計画失敗・離脱を許す |
| 経済が単調に破綻 | 一律に国庫不足・飢饉になる | 所有者・価格・賃金・消費・税の台帳を点検 |
| 詳細シミュレーションが開発を圧迫 | 出生や医療に時間を使い試遊できない | M3到達を優先し、後続を切り離す |
| 複雑でも結局計算で解ける | 特定の定石が支配的 | 定石の存在は許容。感情・不確実性・制度の異なる状況で選択が変わるかを見る |

有限のルールを持つゲームから、最適化そのものを取り除くことは目標にしない。プレイヤーが大切にする対象が複数あり、判断の条件も変わることで、最適化だけでは割り切れない体験を作る。

## 付録A. 実装時の曖昧さを減らす初期仕様

本付録も実装用の仮決定。本文の核を変えずに、初回のコード化で必要になる空欄を埋める。

### A.1 世界生成の固定順

1. seedと設定を読み込み、Schemaを検証。
2. 国、拠点、道、役職、文化、制度を生成。
3. 国ごとにPersonを指定数だけ生成。主要人物もこの人数に含める。
4. 主要人物の値をシナリオ指定で上書きし、追加人口は作らない。
5. 世帯を作り、各人をちょうど一世帯へ割り当てる。初版は世帯サイズ2〜5、余りを最後の世帯へ統合。君主の宮廷世帯も同じEntity。
6. 初期軍籍を付ける。残る人口に職を割当。職場と世帯の初期資産を総量内で分配。
7. 家族・同僚・指揮・地元の関係を生成。家族の年齢矛盾を検査。初版は成人の夫婦・兄弟姉妹を優先。
8. 文化から価値分布を生成し、主要な規範を初期認識に登録。
9. 個人ごとに知識を初期化。地理の一般知識と軍事上の最新情報を分ける。
10. 不変条件、収支、人口、役職兼任、Command権限を検査し、開始snapshotを保存。

### A.3 所有・家計・給与の一意化

- 各Personは個人口座、各Householdは家計口座、職場・国・政治運動も口座を持つ。
- 給与は雇用主口座→個人口座へ。定例所得税を個人口座→国庫へ支払う。
- その日の税後給与の80%を世帯へ拠出、20%を個人に残す。割合は制度・契約として保持し、初版では全員同じ。
- 世帯は家計で食糧を買う。家計不足時は世帯内個人が、家族への価値と自分の生活余力で追加拠出を判断する。
- 軍の給与も同じ家計拠出を使える。ただし遠征地から送金する場合は送金便Messageと資産の輸送を生成し、即時に家族へ届かない。M1の地図未実装時だけ同拠点扱い、M2で輸送へ置き換える。
- 約束した家族扶助は対象Householdへ支払う。通常の給与拠出とは別債務。
- 職場所有者の取り分は、その職場の残金からのみ支払う。残金がなければ賃金未払の債務が生じる。自動補填しない。
- 行政の賃金と兵士給与は国庫、商業・輸送の賃金は各事業主口座から支払う。商業・輸送は実際の取引手数料・輸送契約から収入を得る。初版手数料は取引額の5%で端数切捨て、どの勘定からどこへ払ったかを残す。
- 税の小数は人物別に端数繰越を持つ。毎日3通貨の10%を切り捨て続けて無税になる問題を避ける。

日次処理の清算順は本文第5章を守り、市場で不足した家計は翌日に需要を繰り越す。開始日の世帯資産と食糧備蓄も検証し、清算の順序だけを原因として全員が飢えないようにする。過去の未購入分は、翌日に必要食糧を無制限に積み増す債務にはせず、欠食履歴として残す。

### A.4 戦闘の士気と移動

初期の個人士気は0.65を基準とし、隊長信頼・従軍契約の評価から±0.2の補正。毎分の更新は次をたたき台にする。

```text
moraleDelta = -0.50 × newlyLostFraction
              -0.015 × nearbyFleeingFraction
              -0.010 × fatigue
              -0.010 × hunger
              +0.004 × commanderConfidence
              +0.003 × safeRest
```

`newlyLostFraction`は所属部隊の「その1分に新たに戦闘不能になった人数／その1分開始時の戦闘可能人数」。直近5分の損害率は恐怖の評価に使うが、同じ死者を毎分新規損失として再加算しない。`commanderConfidence`は−1〜1で、命令が届いていない場合0。`safeRest`は非接敵かつ休息命令中に1、それ以外0。

初期逃走判定は `morale - 0.3×fear + 0.2×trustInCommander < 0.2`。撤退命令による秩序ある離脱と、恐慌による逃走は別状態。再結集には安全地点と30分の休息を要する。

戦場移動は最大1セル/分、森林は2分/セル、川は橋のみ。相対位置と接敵判定の更新順を固定する。近傍は隣接8セル。高地から低地への攻撃補正1.15、森林は被攻撃exposure0.7。地形補正を双方に二重適用しない。

兵士位置は部隊セル内のオフセットと状態を持つ。会戦初版ではセル内で個別の物理衝突を解かない。この抽象化を仕様として明記し、実際には集団計算なのに個別剣戟を完全再現していると説明しない。

### A.5 外交が実際に成立するための最低仕様

NEGOTIATEはOfferを作り、相手へ送る。Offerは提案者、相手、条項、対価、期限、関連Promiseを持つ。相手到着後に通常AIが評価し、承諾・反対提案・拒否を返信する。

M3の条項：通行権、通行料、不可侵、捕虜返還、資源移転。通行権は対象経路、許可対象、期限を明記し、軍の通行と商用通行を分ける。シナリオ目標は商用通行権の確保とする。

敵領主の初期受諾式：

```text
acceptScore = 0.35×materialGain + 0.25×securityGain
              +0.20×trust + 0.20×normFit
              -0.30×prestigeLoss -0.30×perceivedMilitaryOpportunity
```

各項0〜1、0.25以上なら受諾、0.10以上なら一度だけ対価を20%増やす反対提案、それ未満は拒否。対価だけで全状況を突破できないよう、最低限の制度上の禁止条項は候補生成で除外する。これらも本人の認識から計算する。

試作では敵国に「有料の商用通行は正当」という規範を初期設定し、軍事と外交の両方が成立可能にする。物的利益は提案額／相手の30日分行政・軍費を0〜1へ正規化。安全利益は不可侵の有無と相手への信頼、名誉損失は公的な屈服要求の有無から算出。各入力を開発画面で追えるようにする。

受諾後、必要資源が予約できることを再検証して条約を発効。発効通知が届くまで現地の門衛が即座に方針を変えない。通行拒否が単なる伝達遅延なら、君主の意図的な条約違反と区別する。

### A.6 最小UIの操作手順

1. 起動画面で「峠と収穫」「seed」「通常／開発モード」を選ぶ。
2. 地図で首都を選び、君主・国庫・現在の課題を見る。
3. 報告から人物画面へ移動し、面談・任命・約束を選ぶ。
4. 約束フォームで条件・対象・報酬・期限を設定し、既知の支払能力を確認して送る。
5. 戦略地図で目的地と担当者を選び、軍の任務と撤退条件を指示する。
6. 一時停止／1時間進める／1日進める／連続進行を使う。重要報告到着時は設定に応じて停止。
7. 会戦開始時は布陣済み部隊と既知の敵を表示し、追加命令は伝令到着待ちとして表示。
8. 結果報告から死傷者、約束の発動、関係の変化を辿る。
9. いつでも保存・再開。終了時は目標成否と社会の変化を見る。

1日進める操作でも全イベントを順番に解決し、途中の重要報告では停止できる。高速化により伝令・約束期限・戦闘を飛ばさない。
